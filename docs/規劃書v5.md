# 1. 專案目標、範圍與固定決策

## 1.1 保留的網站主軸

【承接 v4 §1、§4、§6】WordPress 管文章、分類、標籤、頁面、影片、Podcast、選單與媒體；Laravel 管公開頁面、SEO、搜尋聚合、商品、購物車、模擬結帳與商務後臺。兩者只以 REST 與受驗證事件整合，不互相直寫資料庫。

第一版為正體中文個人影音內容站。公開訪客不用註冊，兩套管理後臺各自登入，不做 SSO、不引入 WooCommerce、WPGraphQL、Corcel、React／Vue SPA、Kubernetes、影片轉碼與 AI 自動發文。

## 1.2 三個交付層次

| 交付 | 使用者實際能做的事 | 必須有的工程成果 |
|---|---|---|
| A：可發布的內容站 | 在 WP 編輯、預覽、發布、排程、撤下；訪客閱讀與播放 | 真實 WP＋Laravel＋MySQL、REST 契約、測試、備份／部署腳本 |
| B：模擬商店 | 商品管理、購物車、模擬訂單與庫存 | 伺服器計價、交易與併發控制、後臺權限、個資最小化 |
| C：雲端營運 | 關掉主公的電腦與 Claude 會話後，網站仍可運作 | 常駐主機、DNS／HTTPS、監控、異地備份、還原與回復紀錄 |

**A 可先部署，不必等 B。** 但商店未驗收前，路由與導覽確實關閉；不是只把按鈕藏起來。B 可在 staging 完成，正式站維持 `COMMERCE_MODE=disabled`，待主公核准後才開 `simulation`。

## 1.3 技術棧

| 層面 | v5 固定方向 | 不接受的替代 |
|---|---|---|
| 程式施工 | Claude Code 官方雲端會話 | 本地 Windows／WSL／桌面 CLI 代替雲端 |
| 版控 | GitHub `Whenwhoengine/mysite` | 只把成果留在聊天視窗或臨時 VM |
| 獨立驗證 | GitHub-hosted Actions Linux runner | 要主公開著本機 runner |
| 開發與部署封裝 | Docker Compose、多階段建置 | 正式主機臨時手工裝一堆未記錄套件 |
| 執行語言 | PHP 8.5 已修補維護線 | 直接沿用雲端預裝 PHP 而不查版本 |
| 應用 | Laravel 13.x＋Blade＋原生 CSS／JavaScript | 沒必要的 SPA、大型前端框架 |

| 資料庫 | MySQL 8.4 維護線；各環境同系列 | 因雲端預裝 PostgreSQL 就換架構；SQLite 充當整合驗收 |

【官方查證】Laravel 的正式部署文件要求合適 PHP 執行環境與公開入口設定；Docker 文件亦支援在單一伺服器以 Compose 部署。本案採此組合，但容量與穩定性仍須實測。[S07][S18]

## 1.4 版本決策不等於把舊版本寫死

2026-11-05 查核到的參考基準：PHP 2026-10-21 修補公告包含 8.5.12；WordPress 7.1.4 發布紀錄為 2026-10-28；Laravel 13 文件要求 PHP 至少 8.3。這些是**查核快照**，不是宣稱施工日永遠沒有更新。[S16][S17][S19]

M0 應查實際正式版本、容器標籤與 digest，寫入 `infra/versions.env`、`docs/versions.lock.json`。禁止使用未鎖定的 `latest` 作正式發布依據，也禁止在無來源時自行寫一個看起來合理的 SHA。

保留 `session.upload_progress.enabled=0` 作 PHP 啟動設定；本次讀到的 PHP 公告仍建議這個緩解措施。是否已有後續修復，施工日重查，不以設定一行取代完整更新。[S16]

# 2. 全雲端架構與能力界線

## 2.1 三層運作圖

```text
主公的瀏覽器
  ├─ Claude Code 雲端：交辦、看差異、讀測試結果
  │    └─ 臨時 Linux VM：編輯程式、Docker Compose、合成資料、瀏覽器測試
  ├─ GitHub mysite：原始碼、規劃、工作分支、PR、Actions、版本紀錄
  │    └─ GitHub-hosted runner：乾淨重建、整合測試、映像建置、發布閘門
  └─ 雲端主機商／DNS 控制臺：一次性授權、費用與帳戶管理
       └─ 常駐 Linux VPS
            ├─ Nginx：公開 HTTPS 入口
            ├─ Laravel PHP-FPM＋worker＋scheduler
            ├─ WordPress PHP-FPM＋WP 排程
            ├─ MySQL：WP 與 Laravel 分庫、分帳號
            ├─ 持久化媒體與受限設定
            └─ 加密異地備份、監控與告警
```

**沒有任何箭頭經過主公本地 Windows 的 PHP、資料庫、Docker 或檔案共享。** 主公關閉瀏覽器不應讓已部署的網站停止；正式資料也不得只存在 Claude 開發會話裡。

## 2.2 官方雲端現況：只列與本案有關的事實

【官方查證，施工日重查】

1. 官方雲端會話可在瀏覽器連 GitHub；新專案應先有含 README 的儲存庫。本案已符合初始化條件。[S01]
2. 雲端環境文件列有 Docker、Compose、PHP／Composer、Chrome、git／gh；**工具存在不代表版本適合本案**。[S03]
3. Setup script 有快取建置時間限制，快取保存檔案而非運行程序；服務每次會話都要檢查並啟動。[S03]
4. 會話可能因閒置而被回收；不要把程序、排程或資料唯一副本寄託於會話。[S02]
5. GitHub Pages 是靜態託管；它不能作本案 PHP＋MySQL 的正式執行平台。[S06]

其餘本章的服務配置、權限與續作流程均是【v5 決策】，不是 Anthropic 的預設保證。

## 2.3 主路線與純雲端備援

### 主路線 A：Claude 雲端直接跑 Compose

在單一 `mysite` 會話中建立程式與 Compose，啟動真實 MySQL、WP、Laravel。Claude 自己執行 CLI、HTTP 與瀏覽器測試，將程式推到工作分支；Actions 再從乾淨 runner 重建一遍。

### 備援路線 B：Claude 寫程式，Actions 執行受限工作

當 Claude 雲端無法拉某個映像、Composer 的上游封存檔遭 GitHub proxy 擋住，或 VM 資源不足，**不轉回本機**。改由 Actions 在雲端完成依賴建置、Compose 測試與截圖，Claude 讀回該 commit 的結果、修正並重跑。

這條備援不是「不測就交付」；每次結果要綁定 commit SHA。若只在 Actions 驗證成功，報告明寫 `execution_backend=github-actions`，不得聲稱在 Claude VM 已成功啟動。

### 外部主機未準備好

繼續完成 A、B 程式及 CI，交付 `READY_FOR_STAGING` 候選版、部署包與缺件清單。網站永久網址、正式 HTTPS、真實備份目的地與持久化驗收，仍為未完成。這是清楚的交付界線，不是理由讓 AI 不寫程式。

## 2.4 不需要什麼、仍需要什麼

**不需要**：本地開發套件、GPU 租用、自購代理服務、長開 Windows 電腦、以 Anthropic API key 才能使用的自製雲端程式代理。

**仍需要**：可使用官方 Claude Code 雲端的帳戶、GitHub 存取授權、可用的 Actions 額度；真正公開營運另需要主機、儲存、DNS／網域與部署權限。

主機、網域與外部儲存不因 Claude 訂閱或促銷點數而自動具備。**本版不推定任何促銷額度能支付第三方主機**；費用由實際帳單與供應商方案確認。雲端模型用量與主機帳單分開記錄。[S02]

以 `main` 為起點，使用獨立的 `mysite-build` 雲端環境；權限模式選可實作的模式，不停留在只提計畫的模式。先採官方 Trusted 網路設定，需要時按第 5 章增補核准網域。[S01][S03]

## U4：貼上附錄 A 的完整開工指令

Claude 應從 M0 開始盤點、建立程式並測試，不是再把本規劃改寫一次。它可自行處理命名、程式細節與合成資料；只有帳戶權限、支出、秘密與正式公開變更才需要主公操作。

## U5：一次性建立 GitHub 保護與發布環境

當首個基礎 PR 通過時，由主公在 GitHub 網頁核准合併，設定 `main` 的保護規則與 `staging`／`production` 環境。環境保護能力受儲存庫可見性與方案影響，設定時確認畫面實際可用功能。[S11]

若 workflow 權限被拒，Claude 必須交代確切檔案與錯誤；透過 GitHub 網頁授權或提交經審核的 workflow，**不要求安裝本機 CLI 來繞過**。

## U6：網站需要常駐網址時才處理主機與 DNS

主公提供既有主機資訊，或核准新主機費用。以雲端控制臺的瀏覽器終端完成第 13 章的首次安裝，之後交由已審核的自動部署流程接手。

沒有資源就先列 `BLOCKED_EXTERNAL`；Claude 仍繼續做其他程式與測試。不得自行購買服務或借用不明免費主機。

## U7：正式上線授權

主公在 GitHub `production` 環境審核該版本的測試、備份與回復方式，再核准發布。後續可授權「符合既定門檻則自動部署到 staging」，正式發布的授權範圍另行記錄。

### U0–U7 的最低人工投入範圍

主公負責帳戶與資產授權、費用、網域、2FA 登記、正式發布決定；Claude 負責程式、腳本、測試、錯誤修復、文件與可執行部署產物。不能把一般程式問題逐一丟回主公，也不能把「獨立製作」解釋成擁有主公尚未提供的密碼或付款權限。

# 5. Claude 雲端初始化、依賴與網路

## 5.1 雲端能力預檢：先測，後裝

Claude 必須先建立並執行 `scripts/cloud/preflight.sh`。以下是第一版腳本骨架，執行範圍只有雲端會話：

```bash
#!/usr/bin/env bash
set -Eeuo pipefail
umask 077

root="$(git rev-parse --show-toplevel 2>/dev/null)" || {
  printf '%s\n' 'BLOCKED: 找不到 Git 工作目錄。' >&2
  exit 20
}
cd "$root"
mkdir -p .runtime/evidence
report=".runtime/evidence/cloud-preflight.txt"

{
  printf 'utc=%s\n' "$(date -u +%FT%TZ)"
  printf 'os=%s arch=%s\n' "$(uname -s)" "$(uname -m)"
  printf 'commit=%s\n' "$(git rev-parse HEAD)"
  git status --short
  for tool in git docker php composer node npm curl jq; do
    if command -v "$tool" >/dev/null 2>&1; then
      printf 'tool=%s present=yes\n' "$tool"
    else
      printf 'tool=%s present=no\n' "$tool"
    fi
  done
} > "$report"

if [[ "$(uname -s)" != "Linux" ]]; then
  printf '%s\n' 'BLOCKED: 本案只在雲端 Linux 執行。' >&2
  exit 20
fi

if ! command -v docker >/dev/null 2>&1; then
  printf '%s\n' 'BACKEND=github-actions; Docker CLI 不可用。' >> "$report"
  exit 21
fi
if ! docker info >/dev/null 2>&1; then
  printf '%s\n' 'BACKEND=github-actions; Docker daemon 尚不可用。' >> "$report"
  exit 21
fi
if ! docker compose version >> "$report" 2>&1; then
  printf '%s\n' 'BLOCKED: Compose 不可用。' >&2
  exit 21
fi
printf '%s\n' 'BACKEND=claude-cloud-compose' >> "$report"
printf '%s\n' '預檢完成；尚未代表網站或依賴已驗收。'
```

**限制**：不列印 `env`、token、帶密碼 remote URL 或完整配置。退出碼 21 代表切換純雲端備援，不代表放棄開發。若現有 daemon 可由官方允許方式啟動，記錄實際做法後重測，不在其他主機任意啟動 root 服務。

## 5.2 Setup script 與 SessionStart 各做什麼

【官方查證】環境 Setup script 與儲存庫 SessionStart hook 的執行時點、快取行為不同；單一儲存庫的一般雲端會話可使用 repo hook，但 Projects 的雲端 threads、多儲存庫會話存在不同限制。[S03][S04]

【v5 決策】

| 位置 | 做的事 | 不做的事 |
|---|---|---|
| 雲端環境 Setup script | 輕量工具預檢、必要系統套件準備 | 克隆網站到固定路徑、放秘密、建正式 DB、啟動正式網站 |
| `session-start.sh` | 確認 repo、讀狀態、檢查程序是否需恢復 | 每次重建資料庫、每次改密碼、每次 `composer update` |
| `bootstrap.sh` | 第一次建立程式／依賴／合成資料，之後可重複執行 | 刪掉已有網站或將測試資料灌進 production |
| `up.sh` | 啟動已定義的 Compose 開發服務 | 假設 Setup cache 裡的程序還活著 |
| `doctor.sh` | 讀回 Web PHP、DB、API、排程與健康狀態 | 只看 CLI 就宣稱全站安全 |

初次環境可以沒有自訂 Setup script，讓 Claude 在可見會話中完成預檢，避免啟動前就被耗時安裝卡住。確定可重複的工具準備後，再放進快取腳本。

## 5.3 SessionStart 設定範例

此配置使用官方 hook 格式，腳本名稱為本案命名。新增後須用新會話或依官方方式重新載入，不假設正在執行的會話會自動重跑。[S04]

```json
{
  "hooks": {
    "SessionStart": [
      {
        "matcher": "startup|resume",
        "hooks": [
          {
            "type": "command",
            "command": "bash \"$CLAUDE_PROJECT_DIR\"/scripts/cloud/session-start.sh",
            "timeout": 120
          }
        ]
      }
    ]
  }
}
```

`session-start.sh` 應檢查 `CLAUDE_CODE_REMOTE`、Git 根目錄與 `docs/state/status.json`；缺檔時回報，不自動刪除重建。耗時 build 不塞進 120 秒 hook；由 Claude 在會話內明確執行並保存結果。hook 未執行時，附錄 A 已要求人工觸發相同腳本，所以專案不依賴單一 hook 才能啟動。

## 5.4 網路白名單與相依下載

先用官方 Trusted 設定；只有實際失敗的必要來源才新增。以下只是**候選來源**，是否已在預設清單與是否有轉址，要依施工日官方資料及 log 核對：[S03]

| 用途 | 檢查方向 | 處置 |
|---|---|---|
| PHP／MySQL 映像 | Docker 官方 registry 與其實際內容下載來源 | 查被阻擋的精確 host，核准後補入，不開整個網際網路 |
| Composer | Composer、Packagist 與套件 dist 來源 | 不把廣權 GitHub token 填入 `auth.json` 當萬用解法 |
| WordPress | WordPress 官方發行／checksum API | 版本與語系一起確認，不用未知第三方整合包 |
| ACF | ACF 官方下載與更新來源 | ZIP SHA-256 入版本清單，避免同名供應鏈誤認 |
| npm／瀏覽器測試 | npm registry、Playwright 官方下載來源 | 不關 TLS 驗證；封鎖就改 Actions 執行 |
| 本案 artifact | `mysite` 的 Actions API 與其核准下載轉址 | 檢查來源 commit 與雜湊，不拉最新同名檔冒充本次結果 |

### 特別處理：GitHub proxy 與 Composer

官方文件目前說明：GitHub API／封存檔對未附加 repo 可能遭拒、GraphQL 有限制；一般 npm／Composer 下載因此仍需實測，不應宣稱 Trusted 等於所有依賴保證可抓。[S03]

如果套件 dist 因上述限制失敗：

1. 保存去秘密化的 host、HTTP status、套件與 lockfile hash。
2. 確認是來源限制，不是版本不存在、DNS 或 TLS 錯誤。
3. 改由 `sandbox.yml` 在 Actions 安裝並驗證。
4. 如需帶回依賴，產生只含公開依賴與必要建置工具的 artifact／映像；與 lockfile、Linux 架構及 PHP 擴充相綁定。
5. 以本 repo 的 artifact API 或已核准 registry 讀回；若讀回亦受限，保留所有執行於 Actions，Claude 讀取測試摘要與 screenshot 索引。
6. 不為下載一個套件而附加主公所有儲存庫、不使用來路不明鏡像、不把 proxy 的佔位 token 當真實 registry 密碼。

## 5.5 套件安裝與重現性

首次建立 Laravel 時，官方 `create-project` 目標是空的 `app/` 子目錄；精確版本由 M0 查核決定。正式骨架存在後只依 lockfile `composer install`，不在每次啟動做 `composer update`。Composer 的 install、audit 與 platform requirement 檢查有各自目的，三者都要留證。[S22]

Node 只負責前端建置與 E2E；正式 Web 不跑開發伺服器。初次產生 lockfile 後用 `npm ci`，建置依賴不帶入 PHP 執行映像。套件來源不明或插件要求執行安裝腳本時，先審核允許範圍，不全面關閉安全檢查。

# 6. 容器、資料與中斷續作

## 6.1 服務分工

下列均為本案擬定服務名稱。正式版本必須沿用同一組定義，差異透過 Compose override 與設定注入，不另外手刻一套無法重現的正式環境。

| 服務 | 職責 | 持久資料／對外限制 |
|---|---|---|
| `gateway` | Nginx，依主站／CMS host 路由，HTTPS 與安全標頭 | 正式只公開 80／443；開發只綁雲端 VM loopback |
| `app-web` | Laravel 靜態資產與 FastCGI 入口 | 只暴露容器網路；根目錄為 Laravel `public/` |
| `app-php` | Laravel PHP-FPM | 程式唯讀；只必要 storage／cache 可寫 |
| `app-worker` | Laravel database queue | 與應用同版映像、同必要設定；不公開埠 |
| `app-scheduler` | Laravel scheduler | 每環境單一排程實例，具心跳與重複執行鎖 |
| `wp-web` | WP Web 入口、管理靜態資產與公開媒體 | 不直接暴露 FPM；上傳目錄不得執行 PHP |
| `wp-php` | WordPress PHP-FPM | WP 程式／外掛唯讀，uploads 持久化可寫 |
| `wp-jobs` | WP-Cron、outbox 投遞與事件對帳 | 單一排程控制，與 WP 同版程式及必要憑證 |
| `mysql` | MySQL 8.4 維護線 | 兩個 database、各自帳號；不設公網 port mapping |
| `test-runner` | 契約、E2E 與安全測試 | 只在 dev／CI profile 啟動，正式不常駐 |

可以由同一映像以不同啟動命令執行 PHP、worker、scheduler，但不可讓佇列與排程藏在某個 Web request 裡。初期不增加 Redis；容量不夠先量測、調整 worker 數，不盲目堆服務。

## 6.2 映像建置原則

1. 以查證的官方 PHP 基底建立共用工具鏈，再分 Laravel 與 WP runtime；兩個 FPM 服務／使用者隔離，不共用可寫程式目錄。[S20]
2. WordPress 核心依指定版本取得，核對官方 checksum；自製外掛與已核准外掛複製進映像。核心驗證不取代外掛來源驗證。[S25][S26]
3. `app-web` 與 `app-php` 的應用路徑必須一致；WP Web 與 FPM 也一致。Nginx `SCRIPT_FILENAME` 不得指向另一個容器不存在的路徑。
4. 正式映像不掛開發原始碼 bind mount；部署以 immutable digest 指定，禁止登入正式容器臨時改 PHP 檔。
5. `.dockerignore` 排除 `.env`、`.runtime/`、`.git/`、DB dump、秘密、個資與測試報告。掃描映像內容與 history，不只掃 Git。
6. 依賴安裝需要秘密時使用建置 secret mount，不以 Dockerfile `ARG`／`ENV` 寫入可留存的秘密。[S10]
7. Laravel 的環境專屬 config cache 在注入設定後建立，不在無正式設定的 CI build 階段把預設 URL／APP_KEY 烘焙進映像。
8. 共用 code layer 不代表共用秘密。WordPress 不取得 Laravel `APP_KEY`，Laravel 不取得 WordPress DB 密碼。
9. 正式 runtime 不裝 node_modules、編譯器或開發除錯工具，除非有明確且核准的必要用途。

## 6.3 PHP 安全設定與實際 HTTP 驗證

`infra/php/security.ini` 至少包含本次明確需要的緩解設定：

```ini
session.upload_progress.enabled=0
expose_php=Off
display_errors=Off
log_errors=On
```

其餘上傳大小、記憶體、執行時間與錯誤 log 目的地在設定目錄統一管理；dev／CI 可增加偵錯，但不能隨正式映像打開公開 stack trace。

`doctor.sh` 應分別透過 Laravel 與 WP 的 **HTTP→Nginx→FPM** 路徑驗證有效值。可使用僅內部可達的診斷 endpoint 回傳白名單欄位；**不能公開 `phpinfo()`**。完成後保留受保護的最小機器檢查，公開健康回應只顯示 OK／不可用，不暴露版本或路徑。

驗收至少記錄：兩個 Web SAPI、PHP 精確版本、設定是否為 0、請求經過的服務、commit、映像 digest 與日期。CLI 檢查只是附加證據，不是取代 Web 檢查。[S16]

## 6.4 MySQL 初始化與帳號

【承接 v4】同一環境可共用一個 MySQL 服務，但建立 WordPress 與 Laravel 兩個資料庫、兩組受限帳號。這是邏輯與權限隔離，**不是硬體隔離**。staging 與 production 至少分 Compose project、volume、database 與秘密；正式資料不得掛到 CI。[S21]

- `mysql` 不公開 3306；FPM 不公開 9000。
- root 帳號只供首次初始化／受控維護，不放進應用設定。
- 初始化程式只在空資料卷建立 schema／使用者；不能以重啟容器來暗中重設密碼。
- 既有 volume 的密碼輪替是獨立作業：更新 DB 使用者、更新秘密、重啟相關程序、驗證，再撤銷舊秘密。
- 字元集採 `utf8mb4`；collation 經中文與 emoji 測試選定，所有環境一致。
- Laravel schema 只由 migration 管；WP schema 只由 WP 與本案外掛的版本化升級管。
- commerce 為純模擬，不存在真實交易資料；未來要接真實交易必須另案建立隔離資料庫／部署，不把現有資料改旗標就當真實訂單。

## 6.5 秘密與持久化

【v5 決策】開發秘密放 `.runtime/secrets/`，目錄限 owner 存取。正式秘密放主機專用受限目錄或核准的 secrets 管理服務；Compose secret 可限制容器取得哪些檔案，但**不自動代表來源檔已加密保存**。[S08]

正式持久化內容包括 WP uploads、MySQL 資料卷、Laravel 必要檔案、TLS 狀態、備份索引與秘密的受控備援。程式碼、WordPress 核心與外掛應從版本成品重建，而不是以整個可寫 `wp-content` 資料卷掩蓋新版外掛。

禁止的操作：對 staging／production 執行 `docker compose down -v`、全域 `docker system prune --volumes`、`migrate:fresh`、無範圍清空資料夾。清理臨時測試資源也須核對 project ID 與 CI 環境標記。

## 6.6 雲端中斷與續作

每個工作切片結束時，`checkpoint.sh` 必須更新：

- `docs/state/status.json`：目前階段、目前 commit、執行後端、已通過／未跑測試。
- `docs/state/tasks.json`：任務依賴、完成條件與狀態。
- `docs/state/blockers.md`：外部缺件、具體錯誤、已做的排除，不能只有「有問題」。
- `docs/state/next-step.md`：下一個可執行動作、必要命令、不可碰的資料。
- 已提交分支與遠端 commit：未推送須明記，不能將本地 commit 當雲端永久保存。

**新會話復工順序**：讀 `CLAUDE.md` → 讀 state → 確認 Git／遠端差異 → 預檢 Docker／網路 → 依 lock 重建 → 只灌合成資料 → 執行上一個最小驗收 → 繼續未完成任務。

程式與測試依賴 Git／映像／lockfile 恢復；正式文章與媒體依常駐主機與備份保存。兩者不可混為一談。重建開發 VM 不能被視為正式站災難復原演練。

# 7. WordPress 內容工程

## 7.1 內容模型與範圍

| 型別 | 首版狀態 | 必填內容 | 備註 |
|---|---|---|---|
| `post` | 必做 | 標題、slug、正文、摘要、作者、分類／標籤、封面／替代文字、狀態與日期 | 專欄可先用分類，不再增一套重複表 |
| `page` | 必做 | 標題、slug、正文 | 關於我、隱私說明、聯絡方式；首版不收聯絡表單 |
| `video` | 必做 CPT | 標題、摘要、YouTube URL／ID、封面、分類、選填片長 | 不用 API key 也能先完成合法 URL 嵌入 |
| `podcast` | 必做 CPT | 標題、簡介、核准音訊 URL／附件、封面、分類、選填時長 | 播放與介紹，不冒稱已完成平台分發 |
| `event` | 延後 | 待另案定義活動需求 | v4 表格出現但流程未落實，本版不暗中加入 |
| 品牌設定 | 必做最小集 | 站名、標誌、作者介紹、社群網址、主導覽 | 不依賴付費 Options Page 才能使用 |

每個回傳內容物件含 `model_version`；初版值由契約定義。所有資料保留 WP 為唯一內容寫入端，Laravel 不做第二個文章編輯器。

## 7.2 外掛與欄位來源

`site-content` 負責 CPT、capability、taxonomy 綁定、REST namespace、主站網址映射、preview、outbox 與必要健康檢查。CPT 應開啟正確的 REST 支援，並測試 Gutenberg 能否儲存、預覽與修訂。[S35]

ACF 只作欄位 UI，不與自製外掛重複註冊同名 CPT。首版只採已確認授權的免費欄位能力；需要付費功能先走採購，不以未授權 ZIP 達成。Local JSON 由 `wp/acf-json/` 載入並版控；正式編輯者能改欄位值，但不能在正式站任意改欄位結構。[S28][S29]

登入第二因素候選採 WordPress.org 的 Two Factor，須於施工日查版本與相容性。安裝外掛不代表所有管理員已完成註冊；需逐帳號驗證第二因素與備援碼保管。[S43]

## 7.3 權限與帳號生命週期

| 角色 | 可以 | 不可以 |
|---|---|---|
| WP 站台管理員 | 管理內容與核准帳號、必要系統設定 | 透過編輯器修改正式 PHP 檔或任意安裝外掛 |
| WP 編輯者 | 編輯其核准範圍、發布／撤下、預覽 | 取得 Laravel 商務權限、改外掛與版本 |
| WP 服務帳號 | 只在核准自製 endpoint 執行必要讀取 | 管理外掛、任意建立使用者、取得 admin |
| Laravel 管理員 | 商品與模擬訂單、帳號授權及稽核 | 因 Laravel 登入就取得 WP cookie |

本案 capability 遷移必須可重複執行，只處理本外掛擁有的權限集合；更新前後都測管理員與編輯者。停用編輯帳號時保留文章，將必要內容責任轉交，不以刪除使用者連帶刪文。

服務帳號的 Application Password 代表該帳號權限，不能把它誤認為自動具備細粒度 OAuth scopes；最小權限須靠角色與 permission callback 落實。[S24]

## 7.4 Gutenberg 與富文字契約

首版必須支援：段落、H2／H3、圖片與圖說、引用、列表、連結、分隔線、程式碼、表格、封面圖與分類標籤。建立一篇涵蓋全部格式的驗收文章，從 WP 儲存到 Laravel 實際顯示逐項核對。

WP 可先以 `wp_kses_post()` 等機制處理允許的內容；Laravel 仍需以明確 allowlist 的 sanitizer 作跨系統邊界。不宣稱一個函式會自動滿足本案全部 iframe、CSS 或事件屬性限制。[S36]

Blade 預設文字以 `{{ }}` 跳脫。富文字建立單一 `SafeContent`／等價安全型別與專用元件，只接受 sanitizer 輸出；其他位置的 `{!! !!}` 一律阻擋。CI 檢查的是**未授權的不跳脫輸出**，不是把所有富文字功能一起禁用。[S30]

影片播放器以經驗證 ID 組成自有模板，不接受作者任意貼入 iframe 原始碼。外鏈與圖片 URL 經 scheme／host 檢查；禁止 script、事件屬性與危險 URL。

## 7.5 媒體與未公開資料

- YouTube ID 用合法字元格式與網址 host 白名單解析；格式正確不代表影片存在、可公開播放或有權利使用。
- 音訊採核准來源；需支援 HTTPS、正確 Content-Type 與 Range／206 播放跳轉。
- 第一版不讓伺服器自動抓任意 URL，避免把封面／RSS 功能變成 SSRF 入口。[S37]
- uploads 不可執行 PHP、不能列目錄；限制大小、副檔名與 MIME，測 `.php`、雙副檔名與偽造 MIME。
- **WP 上傳檔的 URL 可被直接取得時，不等於草稿附件保密。** 首版 uploads 只放可公開素材；私人草稿附件不得上傳，除非另做具授權的媒體配送。
- Laravel 預覽頁不得把預覽 ticket、服務憑證或未公開正文送入公共 CDN、分析工具或公開 CI artifact。
- 正式媒體與開發 fixture 分開；沒有主公品牌素材時使用明標的示例，不捏造其履歷、文章或商品。

# 8. 跨系統 API、事件、預覽與快取

## 8.1 明確區分五種網址

| 設定 | 用途 | 範例的性質 |
|---|---|---|
| `APP_URL` | Laravel 對外 canonical | 真實值待主公提供 |
| `WP_PUBLIC_URL` | 主公瀏覽器登入 WP 的網址 | 例如 `cms.<核准網域>`，不是已存在網域 |
| `CONTENT_API_BASE_URL` | Laravel→WP 的內部來源 | 容器內固定服務來源，不能由訪客輸入 |
| `CONTENT_PRIVATE_API_BASE_URL` | 預覽等需要服務憑證的 WP 來源 | 使用可驗證 HTTPS 的核准入口，與公開查詢分離 |
| `CONTENT_EVENT_URL` | WP→Laravel 的內部接收端 | 固定 `/internal/content-events/v1` |

CMS 的瀏覽器網址與內部 API 網址不能互換：若把內部 `wp-web` 名稱當 WP_HOME，主公瀏覽器會被導向不可用的名稱。對外 URL、內部 HTTP 及反向代理 HTTPS 判定均須測試。

公開、無憑證的容器內查詢可依核准私網政策使用 HTTP；Application Passwords 等帶秘密請求必須走可驗證的 HTTPS 入口。開發／CI 使用受控測試 CA 並讓 client 信任，正式用有效憑證；不得使用 `--insecure`、關閉 TLS 驗證或全面解除 WP 的 HTTPS 認證限制來假裝整合成功。[S24]

內部固定服務可有明確私網 allowlist 例外；外部媒體抓取則拒絕私網／metadata endpoint。不能用同一條「所有私網一律禁止」把合法 WP 整合也阻斷。[S37]

## 8.2 內容 REST 契約

WP 註冊 namespace 為 `site-content/v1`，一般 WordPress REST 完整路徑包含 `/wp-json/`。下表為**v5 新案實作契約**，不是宣稱外掛已經提供這些 API。[S23]

| WP 完整路徑 | 用途 | 授權／過濾 |
|---|---|---|
| `GET /wp-json/site-content/v1/health` | CMS 準備狀態 | 不洩露版本與秘密 |
| `GET /wp-json/site-content/v1/posts` | 公開文章列表 | 只含 publish、無密碼保護 |
| `GET /wp-json/site-content/v1/posts/{id}` | 公開文章詳情／可見性 | 狀態與類型雙重確認 |
| `GET /wp-json/site-content/v1/pages` | 靜態頁列表／slug 查詢 | 同上 |
| `GET /wp-json/site-content/v1/videos` | 影片列表／slug 查詢 | 同上 |
| `GET /wp-json/site-content/v1/podcasts` | 音訊內容列表／slug 查詢 | 同上 |
| `GET /wp-json/site-content/v1/content/{type}/{id}/visibility` | 判定仍公開與目前版本 | 只返回必要狀態，不回草稿正文 |
| `GET /wp-json/site-content/v1/taxonomies` | 分類、標籤 | 不洩漏私人內容統計 |
| `GET /wp-json/site-content/v1/menus/{location}` | 選單 | URL allowlist／主站映射 |
| `GET /wp-json/site-content/v1/search` | 跨核准型別的公開搜尋 | `q`、頁碼／游標有上限 |
| `GET /wp-json/site-content/v1/preview/{type}/{id}` | 精確預覽快照 | 服務憑證＋與內容綁定的有效票券 |

列表支援 `page`、`per_page`、分類、標籤及核准排序；`per_page` 設上限，避免無界載入。slug 查詢使用參數契約，找不到回 404，不能假回空文章。

每個 route 必有 permission callback；公開內容 callback 仍要檢查公開狀態、密碼保護與型別，不只是回傳 true。未知方法、型別與無效 ID 直接拒絕。[S23]

### 回應共同結構

```json
{
  "data": [],
  "meta": {
    "api_version": "v1",
    "model_version": 1,
    "page": 1,
    "per_page": 12,
    "total": 0,
    "generated_at": "UTC_ISO8601_AT_RUNTIME"
  }
}
```

日期示例是格式佔位，實作時必須是真實 ISO 8601 值。內容包含 id、type、slug、title、excerpt、sanitized body、公開作者名稱、分類、封面、日期與型別欄位；不回使用者 email、密碼 hash、內部路徑或服務設定。

新增可選欄位可相容擴充；刪除／改語意走 v2，不能靜默破壞 v1。`model_version` 不符回固定錯誤，不把它偽裝成「尚無文章」。

## 8.3 Laravel 整合分層

```text
Controller
  → ContentQueryService
  → ContentRepository
      → WordPressRestClient
      → Content DTO / model_version validator
      → HTML sanitizer / SafeContent
      → Cache + visibility lease
```

Controller 不自行拼 URL、不持有永久密碼。HTTP client 集中管理 timeout、重試、回應大小、redirect、錯誤分類與 allowlist。公開讀取預設只讀公開 endpoint；草稿預覽走獨立方法，不與公開快取共用 key。

初始設計值：連線 timeout 2 秒、整體 5 秒、冪等讀取最多 2 次嘗試。這些是本案起始值，要以測量調整；重試不得將每頁的等待無限拉長。驗證錯誤、401／403、404 不當成暫時性網路錯誤盲目重試。

## 8.4 事件方向與簽章

WP 發送到 **Laravel**：

```text
POST /internal/content-events/v1
```

事件主體固定含 `event_id`、`event_type`、`content_type`、`content_id`、`content_version`、`status`、`occurred_at`。簽章覆蓋實際傳送的原始 body bytes，避免兩端各自重新排序 JSON 造成不同結果。

本案簽章字串規格：`delivery_timestamp + "\n" + event_id + "\n" + raw_body`；使用 HMAC-SHA256，header 帶 key ID 與送達時間。驗簽用常數時間比較，時差窗起始 5 分鐘，伺服器需校時。

每次重試使用新的送達 timestamp 與簽章，但**保留同一 event_id 與同一事件內容**。否則長時間故障後的合法重試會被永久當成過期事件。

- 首次有效事件：持久保存後回 202，交給 queue 處理。
- 相同 ID、相同內容重送：回成功 acknowledgement，不重複套用。
- 相同 ID、不同內容：拒絕並告警。
- 簽章錯誤／來源不符／超出時窗：拒絕，不寫入正文或快取。
- 舊版本事件晚到：只能觸發重新查目前狀態，不得讓舊正文覆蓋較新狀態。

## 8.5 Outbox 不假裝與 WP 儲存完全原子

【v5 決策】`site-content` 建立自己的 outbox table，由發布／修改／撤下 hook 建立事件，不在編輯 request 內同步等待 Laravel。

WordPress 核心儲存與外掛插入 outbox 不能在沒有實作證據時宣稱是同一個原子交易。因此另外做每分鐘對帳：依內容版本、水位與可見性找漏掉的事件並補送。測試要故意讓 hook／outbox 寫入失敗，再確認對帳能恢復。

投遞採有限重試與退避；超限進死信，提供依事件 ID 重播與依內容 ID 重新同步工具。重播有管理授權與稽核，不直接給訪客呼叫。

## 8.6 60 秒撤下上限的可實作規則

**這是本案目標，不是供應商保證；超限測試失敗即不得宣稱符合。**

1. 正文快取與「仍可公開」的證明分開保存。
2. 可見性檢查快取預設 30 秒，硬上限 60 秒；時鐘、快取鍵與最後確認時間都要可測。
3. 收到撤下事件立即清除詳情、列表、搜尋、RSS／sitemap 相關項目並設撤下標記。
4. 沒收到事件也不能無限用舊資料；超過可見性期限必須重新問 WP。
5. 重新確認失敗時停止供應該正文，回 503／適當錯誤，不把「不能確認」當成「仍公開」。
6. WP 明確告知非公開／不存在時，回不揭露私人狀態的 404，不能將草稿標題留在搜尋摘要。
7. 初版不讓 CDN 長期快取公開 HTML；媒體快取獨立。撤下文章不等於撤銷所有曾經公開的媒體 URL。

測試必須包含：WP 撤下後故意丟掉 webhook、再中斷 WP 連線；檢查所有入口不會在硬期限後持續回正文。不能只測「有收到事件」的理想路徑。

## 8.7 草稿預覽

流程：WP 編輯者先儲存目前草稿 → WP 驗證其對該內容的權限 → 產生具體 revision／欄位快照 → 簽發短效單次 ticket → Laravel 交換為短效預覽 session → 以主站版型顯示該快照。

- ticket 綁定 issuer、audience、content ID、type、revision／snapshot ID、期限、jti 與核發者。
- 預設有效期 10 分鐘、最大 15 分鐘；使用後不可重複交換。
- 未保存編輯不得假顯示成已保存預覽；UI 必須先保存或明示需要保存。
- ACF 欄位也須進預覽快照；不能只取得正文 revision，卻顯示另一版的影片 URL／封面。
- 票券進入交換頁後立刻清除網址參數再導向；該入口不載第三方資源、設 `Referrer-Policy: no-referrer`，proxy／應用 log 不記票券。
- 預覽回應 `Cache-Control: private, no-store`、禁止索引，不出現在 sitemap／RSS。
- WP 服務讀取仍驗該票券與內容，不因一把服務密碼就放開所有草稿。
- 過期、錯版、已刪除、跨內容使用與重播都要失敗；不能回正式文章掩飾預覽失敗。

## 8.8 排程、時區與錯誤目錄

主公在 WP 使用 Asia/Taipei；API 輸出明確 UTC 時間，Laravel 再轉展示時區。保存 WP 原生 local／GMT 欄位語意，不直接改其核心 schema。

正式 WP-Cron 由 `wp-jobs` 固定觸發到期工作，Laravel 由獨立 scheduler 執行；零訪客也要能排程發布。WP-CLI 的 `wp cron event run --due-now` 與 Laravel 排程命令需在對應容器、對應設定下執行，加入防重入與心跳。[S27][S32]

| 專案錯誤碼 | HTTP | 訪客訊息／處置 |
|---|---:|---|
| `CONTENT_NOT_FOUND` | 404 | 找不到內容，不揭露私人狀態 |
| `CONTENT_UPSTREAM_UNAVAILABLE` | 503 | 內容暫時無法讀取，可稍後重試 |
| `CONTENT_MODEL_UNSUPPORTED` | 503 | 暫時不可用；內部告警版本不符 |
| `PREVIEW_INVALID` | 403 | 預覽已失效，請由編輯器重新產生 |
| `EVENT_SIGNATURE_INVALID` | 401 | 機器回應，不回簽章計算細節 |
| `RATE_LIMITED` | 429 | 操作過於頻繁，附受控重試資訊 |
| `COMMERCE_DISABLED` | 404 | 商店未開放，不暴露半成品 |
| `SIMULATION_ONLY` | 422 | 此功能僅供模擬，不接受真實交易 |

公開回應帶隨機 request ID，完整診斷留在受限 log；Controller 不自行創造多套互相矛盾的訊息。

| `/cart`、`/checkout`、`/orders/{token}` | Session／旗標控制 | 只做模擬，嚴格授權 |

v4 沒完整列出的 Podcast 詳情、分類與標籤路由在此補齊。既有 URL 尚未存在，沒有「舊站導轉已完成」可宣稱；未來改 slug 時才記錄 301 映射與碰撞規則。

## 9.2 視覺實作要求

【承接 v4】採具影音辨識度、文字易讀的內容站，不是 WordPress 預設主題套殼。深色／高對比方向保留，但可用性優先於裝飾。

【v5 決策】先建立 CSS token 與 Blade 元件：顏色、字體層級、間距、圓角、焦點、卡片、按鈕、導覽、分頁、播放器容器、訊息列與內容正文。所有頁面用同一系統，不各自生成不同風格。

必備版面：桌面、平板、手機。測試 viewport 起始採 1440、768、390 CSS pixels，另外測長標題、長網址、無封面、零篇文章與 200% 縮放。示例文章清楚標示「示例內容」，不可捏造主公發言或公開履歷。

## 9.3 無障礙與效能

WCAG 2.2 AA 是本案目標，不宣稱只跑一次自動掃描就完成認證。[S41]

- 真正標題階層、表單 label、圖片替代文字、鍵盤焦點與 skip link。
- 不只用顏色表達成功／失敗；對比、焦點、觸控目標與減少動態效果都測。
- YouTube／音訊使用者主動播放，避免預設大音量自動播放。
- 卡片與播放器預留尺寸，避免版面跳動；圖片採適當尺寸與延後載入。
- 重要正文伺服器渲染，JavaScript 失敗仍可閱讀文章與使用基本連結。
- CI 測量只是實驗室基線；沒有真實流量不能宣稱已量到真實使用者 INP。另保存 LCP、CLS 與可用性測試條件。

## 9.4 SEO、來源與公開邊界

Laravel 產生 title、description、canonical、Open Graph、RSS 與 sitemap。每頁 canonical 指向主站，不指向 CMS。未發布、預覽、管理、訂單與測試頁不得出現在 sitemap。

CMS 前臺入口導向主站或回受控狀態，避免複製內容；**不要把所有 `/wp-json/` 一刀切封掉而破壞 WP 編輯器**。WP 的 Cookie REST、nonce、媒體、Application Password 與自製 endpoint 都需分開測。[S24]

首版以 WP 自身登入＋2FA 保護管理；若另加 gateway 身分閘門，須驗證 Gutenberg REST、上傳與 Application Password 不會被誤擋。主站和 CMS 採 host-only cookie，不以整個父網域共用 Session。

# 10. 模擬商店、資料模型與權限

## 10.1 商務旗標

```text
disabled → simulation
real → 拒絕啟動商務模組；另案規劃，不存在可直接啟用的實作
```

`disabled` 時所有商務寫入與頁面都關閉。`simulation` 時每個結帳／訂單畫面顯示「模擬操作，不收款、不出貨」，不產生「已付款」或真實交易通知。

第一版不收信用卡、真實收件地址或電話；示範收件欄位用固定合成資料或可選測試代號。日後確實需要聯絡資料，先更新資料清單、告知與刪除流程再開欄位。

## 10.2 資料表規格

| 表／資料 | 要點 |
|---|---|
| `users` | Laravel 管理帳號、hash、角色、2FA；公開註冊關閉 |
| `products` | slug 唯一、標題、描述、價格、狀態、封面；不在 WP 另存一份 |
| `product_variants` | SKU／組合唯一、產品 FK、價格與庫存；無規格商品用單一預設 variant |
| 購物車 | 以 Laravel Session 為主，保存 variant ID、數量與顯示快照；不信任快照價格 |
| `orders` | 不可預測查詢 token 的 hash、模擬狀態、金額、冪等鍵、必要測試代號 |
| `order_items` | 名稱／SKU／單價／數量／小計的下單快照 |
| `inventory_mutations` | 每次增減、原因、訂單關聯與操作者；只追加，不隨意覆寫 |
| `content_event_receipts` | event ID 唯一、內容 hash、處理狀態與次數 |
| queue／failed jobs／cache／sessions | 使用所選 Laravel 版本的 migration，不假設空骨架已自帶所有表 |
| `audit_logs` | 權限、商品、訂單、部署操作的去秘密化稽核 |

v4 的 `cart_items` 表列為未來持久購物車延伸，首版不再與 Session 同時成為兩個權威來源；此項為**明確簡化決策**，不是漏做資料同步。

## 10.3 金額與結帳交易

金額欄位統一 `DECIMAL(12,2)`；PHP 以整數最小貨幣單位或經核准 decimal 型別運算。型別轉換只能在單一 Money 元件中執行，禁止先轉 float 再乘 100。預設幣別 TWD，但仍統一兩位儲存精度；是否顯示小數為格式規則，不影響運算。

結帳順序：

1. 驗證 Session、CSRF、數量與冪等鍵；沒有有效 Session 不能只靠訂單 URL 掃資料。
2. 從 DB 重讀商品、variant、上下架、價格與庫存；忽略前端提交的單價／總價。
3. 開啟 MySQL transaction；依固定 variant ID 順序鎖定必要庫存列。
4. 庫存不足整筆拒絕，不先建立半張訂單。
5. 在同一交易建立訂單、明細、庫存扣減與異動紀錄。
6. 對冪等鍵建立唯一約束，重送返回同一結果；不能靠前端按鈕 disabled 防重送。
7. 成功提交後才排後續通知／背景任務；失敗不發送成功通知。[S31][S44][S45]

取消訂單只允許合法狀態轉換，庫存回補最多一次。禁止刪除明細抹掉歷史，也不能用更新現價回寫歷史訂單。

## 10.4 Laravel 後臺

採 Blade 頁面與 Laravel 的認證／授權能力；2FA 可用官方 Fortify 等相容組件，不因需要驗證就改成 SPA。[S42]

管理動作按 policy 驗證，列出管理員與只讀人員權限；產品更改、庫存調整、取消訂單、匯出資料與停用使用者皆留稽核。密碼重設與正式郵件在取得 mail provider 前只能用測試捕捉器，不宣稱外部信件已寄達。

# 13. 常駐雲端主機：從無主機到可部署環境

## 13.1 正式採用的部署模式

【v5 決策】採 **Linux VPS＋Docker Compose＋主機主動拉取已核准發布**。不要求 Claude 的臨時 VM 直接 SSH 進正式主機，也不在正式主機安裝會執行公開 PR 的 GitHub self-hosted runner。

```text
Claude 雲端 → GitHub 工作分支 → PR 測試 → main 的已驗證 commit
                                            ↓
                              Actions 建置／掃描／推送映像
                                            ↓
                       staging 驗證 → production 環境核准
                                            ↓
                       簽署發布清單 → GitHub Release 成品
                                            ↓ HTTPS 拉取
                 VPS 的受限部署服務 → 驗簽／備份／遷移／換版
                                            ↓
                          外部 HTTPS 冒煙測試＋部署回報
```

這是一項**需要依本版實作與驗收的專案設計**，不是聲稱 GitHub 或 Claude 內建一鍵支援。採拉取模式的理由是：不依賴 Claude 雲端的任意出站 SSH 能力、正式主機不保存 GitHub 寫入權杖，並能在 Claude 會話結束後持續運行。

## 13.2 主機選擇與環境隔離

優先使用主公已授權、能透過瀏覽器控制臺管理的雲端 Linux 主機；沒有既有主機時，先提出供核准的報價，不能自行購買。本版不捏造主機商、區域、IP、付款狀態或促銷資格。

容量起始評估可採以下**工程估算，不是已測容量或價格保證**：

| 用途 | 起始評估 | 必須再測 |
|---|---|---|
| 單一低流量內容站 | 2 vCPU、4 GB RAM、可擴充 SSD | WP／Laravel／MySQL 峰值、備份空間、更新時的額外映像空間 |
| 同主機暫放兩個隔離環境 | 4 vCPU、8 GB RAM 起評估 | staging 測試是否影響正式站；磁碟／CPU／記憶體配額 |
| 正式與 staging | 優先分主機；不必同容量 | 成本核准、環境隔離及故障範圍 |

容量不足先停掉非必要測試、提出擴充，不用關閉安全檢查換效能。媒體主要是圖片與核准音訊，不在本案租 GPU 或執行影片轉碼。

作業系統採 Docker 官方支援的 Linux LTS；本次官方安裝文件包含 Ubuntu 24.04，施工時確認映像、支援週期與套件來源。[S09] 不任意混用 ARM 與 x86_64；版本清單預設 `linux/amd64`，變更平台須重新建置與測試。

staging 與 production 至少分開：Compose project、資料庫、資料庫帳號、媒體 volume、所有應用密鑰、備份儲存前綴、網域與發布簽章公鑰。**不能用同一組正式資料測 staging。**

| P1 | 在雲端控制臺建立／選定 Linux VPS，記錄資源 ID | 已授權的資源清單 |
| P2 | 進入供應商瀏覽器主控臺；取得已審核 commit 的主機 bootstrap | 原始碼及 checksum 可核對；不直接執行未審查的遠端管線 |
| P3 | 安裝核准 Docker／Compose，建立專案目錄及最小權限 | 版本報告、主機重啟驗證 |
| P4 | 建立 staging／production 秘密；設定 GHCR 唯讀取用 | 權限檢查通過；沒有把秘密貼進聊天或 Git |
| P5 | 安裝發布驗簽公鑰、固定部署程式與 systemd timer | 假簽章被拒；未授權清單不能改動服務 |
| P6 | 設定主機防火牆、DNS、HTTP 驗證入口與 HTTPS | 外部端口掃描、可信憑證檢查 |
| P7 | 設定加密異地備份與告警通道 | 備份及告警測試成功 |
| P8 | 執行 staging 首次部署、重啟與還原演練 | M9-A 證據；才能申請正式部署 |

主機尚未開通時，Claude 應把所有能完成的程式、腳本、文件與測試先做完；只把 P1 以後真正需要主機的驗收標外部阻擋。

## 13.4 主機目錄與權限契約

以下全部為**本案擬定路徑**；由 bootstrap 建立並驗證，不是假設供應商已有這些目錄：

```text
/srv/mysite/
├── platform/                    # 已審核、由管理者持有的 Compose／部署程式
├── environments/
│   ├── staging/
│   │   ├── config/              # 不含秘密的環境設定
│   │   ├── secrets/             # 非 Git、受限權限
│   │   ├── releases/            # 清單與換版紀錄，不含客戶資料
│   │   └── state/               # 最新核准序號、部署鎖、現行 digest
│   └── production/              # 相同結構，完全不同秘密
├── tls/                         # 憑證／ACME webroot；私鑰受限
└── backup-staging/              # 加密上傳前的受限暫存，成功後依規則清除
```

資料庫與媒體使用明確命名的持久化 volumes；真實掛載位置由 Docker 查詢，不猜測或硬編碼宿主機底層路徑。應用容器不掛載 Docker socket、不使用 privileged，不讓 WP 管理員修改部署程式或主機秘密。

Docker 控制權具有高權限風險；部署服務的權限應限定於本專案的受控 wrapper。**能部署任意容器不等於低權限**，不能只把帳號改名為 deploy 就宣稱已隔離。

## 13.5 網路與域名

主站與 CMS 採兩個由主公核准的主機名稱；這裡不杜撰實際網域。對公網只發布必要的 80／443；MySQL、PHP-FPM、內部健康檢查、queue 與 Docker API 均不發布公網 port。

Docker 發布端口與主機防火牆互動須實測，不能僅因 UFW 顯示啟用就認定容器端口已封鎖；官方安裝文件提醒相關封包規則問題。[S09]

DNS 操作順序：核對既有紀錄及服務 → 建立核准子網域 → 設定正確 A 紀錄 → 只有 IPv6 全鏈路已可用才加 AAAA → 外部解析查核 → TLS → 入口驗收。不得覆寫其他網站或郵件用的紀錄。

管理網域可以是可解析的公開網址，但必須有登入、2FA、限流及必要的入口限制；「名稱含 admin」不是存取控制。公開媒體的 URL 必須能供訪客讀取；CMS 整站加一道身分閘門時，要測它沒有順便封鎖媒體或合法 Laravel 服務請求。

## 13.6 HTTPS 從零建立，避免啟動循環

【v5 決策】採 Nginx gateway 配合經查核的 Certbot／ACME webroot 流程。Let’s Encrypt 的 HTTP-01 挑戰要求核准網域能經 HTTP 取得指定驗證內容；實際網域與憑證簽發資格仍須驗證。[S38][S39]

1. 第一次先啟動「只提供 ACME 驗證與維護頁」的 HTTP 設定，不引用尚不存在的憑證檔。
2. DNS 正確後，在雲端主機申請憑證；失敗保留維護頁，不能用不可信憑證假標正式 HTTPS 成功。
3. 憑證就緒才載入 443 的主站／CMS 設定，先測 Nginx 組態，再 reload。
4. HTTP 一般路徑轉 HTTPS；ACME 路徑依實際挑戰方式保留。登入與秘密交換不可在 HTTP 上開放。
5. 設定自動續期與 reload hook，實作續期演練及到期前告警。[S34][S39]
6. 反向代理只信任已知來源，確認 Laravel／WordPress 判定 HTTPS 正確，沒有重導迴圈、錯誤 cookie 或混合內容。
7. HSTS 在所有正式子域與 HTTPS 行為確認後才啟用；不在首輪盲加 includeSubDomains 或提交 preload。

## 13.7 正式環境的秘密邊界

正式 DB 密碼、Laravel `APP_KEY`、WP salts、備份解密資料、管理員密碼只存在核准的秘密儲存與常駐主機，不送到 Claude 開發會話。部署簽章私鑰只在受保護的 GitHub environment；主機保存的是驗簽公鑰。

Compose secrets 可將秘密以檔案掛載供容器讀取，但**不自動等同外部 KMS，也不自動加密宿主機檔案**；仍須主機存取控制與加密備份。[S08] Laravel 不會因環境變數名字加 `_FILE` 就自動讀檔，本案必須在受測啟動程式中實作解析；WordPress 設定模板亦明確讀取相應檔案。

所有秘密輪替須有順序與回復方式。不可在每次容器啟動時重新生成 `APP_KEY` 或 WP salts，導致 Session、加密資料與既有整合憑證失效。

# 14. GitHub Actions、映像與受控自動發布

## 14.1 Workflow 分工

以下檔名為本案擬定契約；Claude 必須實際建立，不只在 README 列名：

| 檔案 | 觸發／用途 | 權限與輸出 |
|---|---|---|
| `.github/workflows/ci.yml` | push／PR；格式、靜態檢查、契約、MySQL 整合、E2E | 讀程式；測試結果、合成截圖、無秘密證據 |
| `.github/workflows/sandbox.yml` | 雲端受限時，push 至工作分支或預設分支已有工作流後手動觸發 | 重用 CI 驗證邏輯；結果綁 commit，不接正式秘密 |
| `.github/workflows/release.yml` | 已驗證 main commit 或核准手動執行 | 僅建置工作有 packages write；輸出映像 digest 與來源 commit |
| `.github/workflows/deploy-staging.yml` | 核准候選版 | staging environment；驗證清單、簽署及發布測試環境成品 |
| `.github/workflows/deploy-production.yml` | staging 通過後手動申請 | production environment 核准；相同已測 digest，不重建替換 |
| `.github/workflows/dependency-audit.yml` | 每週及手動 | 稽核依賴與映像；產生報告，不自動部署或改費用 |

第一個含 workflows 的 PR 可能需要先合併才能使用以 default branch 為前提的手動觸發；不能在工作分支尚未有預設分支 workflow 時無限重試 `workflow_dispatch`。GitHub 官方列明事件與分支條件，bootstrap 時逐一驗證。[S12]

Actions 用量、執行資格或帳戶風控若未就緒，標 `BLOCKED_EXTERNAL`，保留已完成程式與可執行測試；不要求主公回本地執行替代方案。

## 14.2 乾淨 CI 的固定順序

1. checkout 明確 commit；所有第三方 Action 以當日核實的完整 commit SHA 固定，記錄對應發布版本與來源。[S13]
2. 驗證版本清單、設定 schema、禁止秘密與危險模式；缺必要鎖定資料即失敗。
3. 建置測試容器；安裝 Composer／npm 的 lockfile 內容。一般 CI 用 install，不使用 update 漂移依賴。
4. 建立本次 job 專屬 MySQL、兩個 DB 及合成憑證；不能從正式環境複製資料。
5. 啟動 WP、Laravel、worker 與 scheduler，完成 readiness 後再測；不能只 sleep 固定秒數就假設已好。
6. 執行單元、契約、整合、安全、權限、撤下期限及故障測試；B 範圍再執行模擬商務測試。
7. 使用鎖定版本的 Playwright 與相符瀏覽器執行桌機／手機 E2E，保存去識別化截圖與失敗證據。[S33]
8. 彙整實際 exit code、JUnit／覆蓋率、版本、來源 commit、測試 ID；失敗仍收集診斷，但不能將 collect 步驟成功當作測試成功。
9. 清理只限本 job 的合成資料與 Compose project；不得使用會影響其他 project 的全域 prune。
10. CI 對相同 commit 的全新環境重建成功，才稱可重現。

**前端測試不是只拍首頁。** 至少包含後臺編輯發布、草稿不能被匿名讀到、預覽撤銷、文章撤下、影音失效、鍵盤操作與商店關閉。外部 YouTube 網路故障不能偽造影片已播放；區分本案內嵌契約測試與外部實際播放檢查。

## 14.3 秘密與 workflow 攻擊面

- PR 的測試只使用合成秘密；fork PR 不取得部署、套件寫入、真實資料或簽章私鑰。
- 不以 `pull_request_target` checkout 不可信 PR 程式後執行帶秘密工作；受權限工作只從已審核的可信分支工作流執行。[S13]
- `permissions` 按 job 最小化；沒有必要的工作只需 `contents: read`。
- 正式核准應綁定確切 commit、映像 digest、測試報告與部署清單；核准後內容改變必須重新驗證。
- workflow、部署腳本、驗簽公鑰與基礎設施變更屬高風險審核路徑；不能以一般文章修正權限直接繞過。
- Artifact、Actions cache 與公開 repo log 不視為秘密庫；不儲存 `.env`、正式 dump、登入 cookie、完整 HTTP 授權標頭或真實草稿。[S15]
- 不能透過手動重新執行任意舊 workflow 取得正式秘密，部署工作必須重新檢查來源與相容性。

GitHub environment 的核准與可用功能依帳戶方案及儲存庫可見性而異。主公目前 repo 為 public，但若之後改私人，必須重查保護功能，不能悄悄降低發布門檻。[S11]

## 14.4 映像建立與版本傳遞

映像應包含程式及編譯好的前端資產，不包含正式設定、媒體、資料庫或管理員。使用多階段建置，正式層不帶測試工具、Node 開發服務或無必要套件。

每個映像保留來源 repo、commit、建置工作與依賴清單。正式部署使用 `registry/image@sha256:...` 的實際 digest，不能只依賴可被改指向的 tag。

GHCR 套件的可見性與 repo 可見性不能視為同一設定；須實查讀取權限。非公開映像由主機使用僅供讀取套件的憑證，禁止使用 Claude 雲端的代理占位 token 當 registry 密碼。[S03][S14]

建置必須使用私有套件憑證時，以 BuildKit secret 等正式機制注入，不以 `ARG`／`ENV` 寫入映像層。[S10] 發布前檢查成品與建置 log；不是把檔案在最後一層刪掉就能消除較早層的秘密。

## 14.5 發布清單與簽章契約

【v5 決策】使用 OpenSSL 支援的 Ed25519 簽章；不自行發明雜湊加密協定。實作要遵循相應 OpenSSL 版本的簽署與驗簽用法，並測試錯誤金鑰、變更一個位元組與錯誤簽章全部被拒。[S48][S49]

發布分兩個物件：

1. **payload**：UTF-8 JSON 的原始位元組，描述已核准的映像與環境。
2. **envelope**：放 `payload_base64`、`signature_base64`、`key_id`、`signature_algorithm`。簽的是原始 payload，不是接收端重新排版後的 JSON。

payload 必備欄位如下，**這是結構範本，null 不可拿來發布**：

```json
{
  "schema_version": 1,
  "project": "Whenwhoengine/mysite",
  "environment": "staging",
  "sequence": null,
  "release_id": null,
  "source_commit": null,
  "created_at": null,
  "expires_at": null,
  "platform_contract": 1,
  "images": {
    "laravel": null,
    "wordpress": null,
    "web": null
  },
  "schema_change_class": null,
  "migration_plan_ref": null,
  "verification_run_id": null,
  "previous_verified_release": null
}
```

`sequence` 是單一環境持續遞增的整數，由序列化的發布工作分配；不能任用可倒退的 commit 時間作序號。以特定 GitHub workflow 的執行序號實作時，必須處理 workflow 重建與重新執行；每次重新授權發布都產生新序號。初次發布、回復發布均遵守同一序號規則。

清單只允許本案核准 registry 與固定 image names；拒絕額外 shell、任意 mounts、任意 service、任意 entrypoint、未知欄位或未支援 platform contract。**MySQL 大版本、主機 Compose、宿主機權限等基礎設施更新另走審核，不由一般網站清單偷偷更換。**

簽章不是「程式安全」的證明，它只證明清單來自持有核准私鑰的發布流程；安全仍依賴上游測試、權限、審核與主機邊界。

## 14.6 拉取發布與抗重播

`pull-release.sh`、`verify-release.sh` 與對應 systemd service／timer 必須實作以下行為：[S50][S51]

1. 每五分鐘左右查核固定的環境 channel；加退避與 API 限流處理，失敗不影響現有網站。channel 名稱是本案設定，不使用「最新任何 release」猜環境。
2. 透過 GitHub Releases REST 取得核准的 channel asset。公開 repo 的已發布成品可公開讀取，因此清單不得含秘密；若改私人，另配置主機唯讀權限。
3. 每個環境發布一個完整 envelope asset；不能先讀到新 JSON、卻拿到舊 detached signature 而形成不一致部署。更新過程遇 404／部分內容就保留舊站，退避重試。
4. 限制回應大小、固定來源，解析 envelope 後先驗證簽章，再解析可信 payload 與執行嚴格 schema 驗證。
5. 核對 project、environment、公鑰 ID、發行／到期時間、單調序號、映像 allowlist 及 platform contract。新清單核准有效期預設 24 小時，屬本案設計；伺服器須有時間同步。
6. 已成功使用相同序號為 no-op；小於已接受序號即拒絕。合法回復也必須以更大新序號指向舊的安全 digest，不能重播舊清單。
7. 取得部署鎖，持久化 pending 紀錄；對失敗的同一清單限制重試次數，避免無限跑 migration。成功才標 active；失敗保留原因與上一可用版。
8. 執行固定部署 wrapper；只將經驗證的映像引用填入既有 Compose 契約。不 `eval` JSON，不執行 release 附帶的任意 shell。
9. 驗證結果與發布歷史保存在受限主機 state；不能讓網站應用程式改寫序號或驗簽公鑰。

channel release／tag 由有相應權限的 Actions 工作管理，不要求 Claude 雲端直接推送 tags。一般 release 成品另保留不可變版本紀錄；channel 只作部署指標，不能取代可追溯的歷史。

私鑰初次在受控雲端環境生成，秘密透過 GitHub environment 設定介面儲存；本機 Windows 不參與。正式主機只需公鑰，生成用的臨時私鑰副本依核准流程清除並保留受控備援。公鑰輪替需雙期信任及撤銷演練，不能讓任何 PR 隨意替換可信公鑰。

## 14.7 主機換版的固定順序

1. 驗簽、拿部署鎖、核對磁碟、DB、備份目的地與上一版資訊。
2. 拉取**全部**新映像並驗證 digest；任何映像失敗，現有服務不動。
3. 建立可辨識的部署前備份；備份失敗即停止換版。首次環境確無資料時，先記錄空環境證據與復原設定，不能捏造上一版備份；有任何既有資料就按一般備份閘門處理。
4. 判斷 schema 改動：優先向後相容的 expand／contract；破壞性變更另案核准，不因自動化就直接執行。首次正式安裝另由受控 bootstrap 建立 WP 與 Laravel 管理帳號，使用該環境秘密並禁止示例 seed；初始憑證只透過核准安全管道交付，不印入公開 log。
5. 必要時進維護模式、暫停會寫相關資料的 worker／排程，完成受控 migration／WP 更新程序。
6. 啟動新應用，檢查 readiness，重啟需載入新程式的常駐 worker，確保 scheduler 只有一個有效執行者。
7. 驗證主站、CMS、內容、撤下與相應 commerce 模式，再退出維護模式。
8. 記錄 active digest／新序號與結果；將外部冒煙測試綁到本次發布。
9. 失敗按第 15 章的相容性決策回復，不能一律 `migrate:rollback` 或還原全部資料。

## 14.8 如何證明確實部署成功

「清單上傳成功」只表示發布申請完成，不是網站已換版。實作受限的 `/internal/deploy-status`，使用獨立唯讀部署監測憑證，只回覆不含秘密的 release ID、狀態與檢查時間；它不暴露 DB 位址、完整設定或套件漏洞資訊。

Actions 等待主機回報匹配 release ID，再執行公開 HTTPS 冒煙測試；等待有上限，超時標 `DEPLOYMENT_UNCONFIRMED`，不能記成功。憑證只在部署環境可用，不進公開監控 log；URL 限固定核准主機，避免憑證被帶去 redirect 目的地。

若無法建置這個受限回報通道，必須以主機的可查核紀錄加外部測試人工核對，並在文件明列仍有人工步驟，不假稱端到端自動完成。

# 15. 備份、還原、回復與災難復原

## 15.1 備份對象與一致性

| 對象 | 必須保存 | 不可採用的替代 |
|---|---|---|
| WordPress | DB、媒體、外掛／核心版本、內容設定 | 只有文章 XML 匯出或只有 Git |
| Laravel | DB、必要上傳、應用版本及設定契約 | 只有 migrations 或測試 seed |
| 機密設定 | 加密保存的 APP_KEY、WP salts、整合與備份恢復所需資訊 | 明文放 Git、Release、Actions artifact |
| 部署 | 固定 Compose、驗簽公鑰、版本清單、回復文件 | 只記一個會移動的 latest tag |
| 法務／刪除處理 | 已核准的刪除／匿名化紀錄與保留策略 | 還原後讓已刪資料重新公開 |

不要直接打包正在寫入的 MySQL 資料目錄冒充一致備份。採與實際 MySQL／表引擎相容的邏輯備份或受支援的一致快照方法，實測還原。大量媒體與資料庫的時間點要協調；必要時短暫停止編輯／上傳、記錄 snapshot ID，不能留下 DB 指向不存在媒體的「成功備份」。

跨 WP 與 Laravel 不宣稱具備分散式交易。備份記錄各系統的一致時間點與內容版本；還原後可重建公開快取／事件投遞狀態，而非把快取當唯一正文。

## 15.2 排程與保存預設

以下均為【v5 決策】，需經成本與資料用途審核：

| 資料 | 排程 | 保存起點 |
|---|---|---|
| WP DB＋媒體增量 | 每日；重大修改／更新前另備 | 日備 30 天；必要月備最多 12 個月 |
| Laravel DB | 每小時；部署前另備 | 小時備 48 小時、日備 30 天；不為模擬個資預設保留整年 |
| 部署／設定 | 每次核准變更 | 與可回復版本生命週期一致 |
| 備份檢查 | 每次確認完成；每週完整性檢查 | 證據至少 90 天，去秘密化 |
| 還原演練 | 每月抽樣、每季完整 | 記錄實測 RPO／RTO 與失敗改善 |

正式上線目標延續 v4：**內容 RPO 24 小時、模擬訂單 RPO 1 小時、主站 RTO 4 小時**。這是目標，不是做到每日 cron 就自動達標；若最近一次有效備份過舊，立即告警並標違反目標。

主機以 systemd timer／已核准排程實際執行，不依賴 Claude 每天在線，也不用 GitHub Actions 的非精準排程取代 WordPress 到期發文或主機備份時效。[S12][S51]

## 15.3 加密異地儲存

【v5 決策】以經查核版本的 restic 作備份封裝與檢查工具；實際目的地可用已核准的相容雲端儲存。restic 的儲存格式具備加密與完整性驗證；是否成功送達、可解密還原仍須實測。[S40][S52]

備份憑證、儲存帳戶與解密資料不可只保存在同一臺 VPS。要有主公／指定維護者可取得的受控復原途徑；沒有解密資料的加密備份不能算可用。異地儲存的刪除權限應盡量與日常寫入權限分開，能提供保留鎖定者另行核實，不假設已啟用。

備份成功後才依保留策略清理暫存與舊資料；清理必須支援預覽、限定 namespace，不能因 prefix 錯誤刪掉其他專案。稽核報告只記 snapshot ID、筆數、時間、大小與結果，不附正式 dump。

## 15.4 乾淨環境還原演練

1. 從雲端建立全新、與正式站隔離的 project／DB／volume。
2. 由版本清單取回相符映像與設定契約，不先升到未測最新版。
3. 取回指定 snapshot，驗證完整性並解密；金鑰遺失或檔案缺損直接判失敗。
4. 還原 WP 與 Laravel DB、媒體及必要設定；阻擋真實郵件、外部事件與公開索引。
5. 套用截至演練日的個資刪除／匿名化清單。
6. 檢查文章、分類、圖片／音訊、權限、草稿不可見、商店模式及訂單／庫存一致。
7. 驗證排程、queue、登入與備份程序可再啟動，沒有把環境指向正式 callback。
8. 記錄開始／結束時間、備份時間點、實測 RTO／RPO、缺漏與修正；結束後依授權清除演練資料。

第一次演練未過，M9 不得 PASS。單純 `restic check` 通過只證明所檢查的儲存結構／資料完整性，不等於整個網站可營運。[S40]

## 15.5 回復決策表

| 問題 | 優先處理 | 禁止 |
|---|---|---|
| 新版程式錯，schema 向後相容 | 用新序號發布上一個仍安全的 digest，保持現有 DB | 回到已知有漏洞版 |
| schema 變更不相容 | 維護模式、保護新寫入、依已審核方案向前修正或受控還原 | 自動 `migrate:rollback` 當萬靈丹 |
| 部分模擬訂單已新增 | 先保留／比對新增資料，必要時進行經核准補償 | 用舊 DB 覆寫導致訂單無聲消失 |
| 媒體誤刪 | 從對應 snapshot 選擇性還原，再驗證引用 | 為一張圖整庫倒帶 |
| 正式主機故障 | 新雲端主機依 bootstrap＋備份重建，確認後切 DNS | 把 Claude 開發 VM 臨時當正式站 |
| 發布私鑰疑似外洩 | 停用 channel 採用、輪替信任金鑰、檢查已發布 digest | 信任後續相同私鑰簽出的清單 |

「回復到舊程式」與「資料還原到舊時間點」是不同操作。後者可能造成資料損失，必須明確授權及保存當前狀態，不可藏在一般 deploy 命令裡。

# 16. 安全、個資、可觀測性與事故處理

## 16.1 最小安全基線

每次正式候選版確認：PHP／WP／外掛已核實安全狀態、Web SAPI 的啟動設定正確、後臺 2FA、登入限流、Session cookie、CSRF、輸入驗證、輸出處理、上傳不可執行、SSRF 目的地限制、秘密不進 Git／映像／log、DB 不公開、備份可還原。

CORS 並非伺服器間 REST 安全措施。本案公開訪客先由 Laravel 同源讀資料，預設不新增跨來源讀取；有必要才對明確 origin、method、header 開放，不能以 `*` 搭配憑證。SSRF 對本案固定內部 WP 來源與一般外部媒體必須分開政策，不能一律禁止私網後反而讓內部整合失效。[S37]

掃描每 PR／發布執行、每週再檢查；高風險未處理或無法判讀的正式執行期漏洞阻擋發版。需要例外必須明列受影響範圍、補償控制、期限及核准者；AI 不能自行簽自己的永久例外。

## 16.2 台灣個資法敘述修正

【v4 原文修正】不再沿用「個資事件一律依法 72 小時通報主管機關與當事人」或「所有權利申請一律 30 天完成」。法規頁面可能同時含已公布但尚未施行的修正；正式上線必須核對生效狀態、業別規範與實際資料處理角色。[S46][S47]

官方權利說明區分：查詢／閱覽／複製本申請的准駁決定原則為 15 日，必要時依法延長；更正、停止或刪除等申請的准駁決定原則為 30 日，延長條件與通知亦須依法處理。**決定期限不是保證任何案件在同一天完成所有技術刪除，也不是任意延後的許可。**[S47]

本案內部程序設計：疑似個資外洩立即限制擴散、保存必要證據、通知指定負責人、查明範圍；由主公／核准負責人依當時適用法律決定外部通知與時限。這項內部立即通報標準不是冒稱法定 72 小時規則。

## 16.3 資料清單與刪除規則

| 資料 | 本版預設 | 需注意 |
|---|---|---|
| 公開文章與影音中繼資料 | 由主公決定發布與保留 | 作者、照片等仍依實際內容處理權利 |
| 草稿、私人內容與修訂 | 不傳到公開快取／證據檔 | 刪除、權限與媒體可見性分開檢查 |
| 購物車 | 七天未活動到期，為專案預設 | 不追蹤無關瀏覽行為 |
| 模擬訂單 | 預設 30 天後刪除或匿名化 | 不收真實地址／電話；必要展示聯絡欄位用合成資料 |
| 稽核與安全日誌 | 預設 90 天可查，之後依用途清理 | 不保存 token、密碼、完整表單；必要 IP 最小化處理 |
| 備份 | 依第 15 章及資料用途限制 | 知會保留期限；還原後套用已核准刪除紀錄 |

保存天數是本案預設，不是通用法定年限。任何新增分析服務、追蹤 cookie、電子報或外部資料接收者都須先更新資料清單與告知，不能由 AI 順手加入。

YouTube iframe、外部封面與音訊請求可能連到第三方；隱私告知應反映實際網域與載入時機。可採點擊後載入播放器減少未操作前的第三方請求，但不能把單一 embed 網域名稱當成完全不追蹤的法律保證。

## 16.4 可觀測性：先可查故障，不先堆大型平台

每個服務至少有：受控結構化 log、存活／就緒檢查、排程最後成功時間、queue 失敗與積壓、WP outbox 死信、備份最後成功時間、TLS 到期與磁碟容量指標。

欄位固定為 `timestamp`、`service`、`environment`、`level`、`event`、`request_id`、`error_code`、必要的去識別化資源 ID。不要記 Authorization、Cookie、預覽票券、連線字串或完整正文。

【v5 決策】初始告警門檻：

- 連續五分鐘 5xx 比例超過 1%，並達最低樣本數；低流量時另以連續探測失敗判斷，避免一個請求造成無意義告警。
- 可見性撤下超過 60 秒、備份逾期／失敗、TLS 即將到期、queue／WP 排程超過容許間隔未成功，立即產生對應告警。
- queue 積壓超過 50 筆作起始提醒，須搭配最舊任務等待時間；不能只看筆數。
- 提醒通道至少一種由主公核准且實測送達的管道；沒有可用寄送憑證時標阻擋，不填一個假 email 當完成。

內容站初始可用性目標可採每月 99.5%，屬工程目標而非對外 SLA。計算明定監測位置、樣本、計畫維護是否計入與統計窗；未滿 30 天只交基線，不假造長期達標報告。

## 16.5 事故分級與行動

| 等級 | 例子 | 第一動作 |
|---|---|---|
| SEV1 | 私密內容外洩、主站全面不可用、未授權部署或重大資料毀損 | 立即限制風險、保存證據、通知負責人；必要時關閉受影響入口 |
| SEV2 | 備份持續失敗、撤下超限、內容事件死信累積、商務完整性異常 | 停止相關寫入／商店、啟動修復與回復評估 |
| SEV3 | 單一影音來源失效、部分頁面錯誤但無資料風險 | 降級呈現、建立修復項，避免誤報全站正常 |
| SEV4 | 小型排版或可用性缺陷 | 記錄、排入工作分支並回歸測試 |

每次事故記錄時間線、影響、證據、處置、回復結果與防再發措施，不憑 log 片段認定攻擊者身分。對外公開說明、正式資料刪除及帳戶權限變更仍依主公授權。

# 附錄 D｜設定目錄、秘密契約與腳本介面

## D.1 設定分層

1. **版控設定**：非秘密預設值、feature flag schema、版本與 API 契約。
2. **環境設定**：實際網域、環境名稱、volume／服務識別；由部署配置提供，不在程式硬編碼。
3. **秘密**：密碼、金鑰、令牌；使用受控檔案／秘密管理注入。
4. **執行狀態**：DB、媒體、queue、快取、發布序號；不能混到 Git 或重建時清空。

專案根目錄為 Compose 插值提供的設定與 `app/.env` 不自動相同，兩者的產生、讀取與路徑必須有腳本明確管理。Laravel 使用 `config:cache` 時，秘密與環境值須在正確執行階段注入，不能把 development 設定烘進 production 映像。

## D.2 非秘密設定目錄

以下鍵名是本案契約，除框架原生鍵外必須由程式實作讀取及驗證；不能只寫入 `.env.example` 就認定生效。

| 鍵／設定 | 預設或來源 | 檢查 |
|---|---|---|
| `APP_ENV` | development／testing／staging／production，部署指定 | 禁止未知值；正式不能是 local |
| `APP_DEBUG` | production=false | HTTP 錯誤不回 stack trace |
| `APP_URL` | 核准的 Laravel URL | 正式 HTTPS、固定 host |
| `APP_LOCALE` | `zh_TW`，依本案語系資源實作 | 缺翻譯不默默變英文正式頁 |
| `APP_TIMEZONE` | `Asia/Taipei`，本案映射至框架設定 | API 邊界轉 UTC，測跨日排程 |
| `WP_PUBLIC_URL` | 核准的 CMS／媒體入口 | 不與 Laravel URL 混用 |
| `CONTENT_API_BASE_URL` | 固定 WP 服務來源＋完整 REST base | scheme／host／port allowlist |
| `CONTENT_PRIVATE_API_BASE_URL` | 核准 HTTPS WP 來源＋完整 REST base | 憑證驗證、固定 host、禁止跨來源轉送認證 |
| `CONTENT_EVENT_URL` | Laravel 事件接收入口 | 固定接收方向，禁止任意 redirect |
| `CONTENT_CONNECT_TIMEOUT_SECONDS` | 起始 2 秒 | 連線逾時；不等於整體請求逾時 |
| `CONTENT_HTTP_TIMEOUT_SECONDS` | 起始 5 秒 | 最多兩次冪等讀取嘗試；重試總時間另控 |
| `CONTENT_VISIBILITY_TTL_SECONDS` | 起始 30 秒 | 端到端撤下最大 60 秒；超限不給舊正文 |
| `CONTENT_BODY_CACHE_TTL_SECONDS` | 起始 300 秒 | 仍受可見性期限約束，不能單獨放行 |
| `PREVIEW_TTL_SECONDS` | 600；硬上限 900 | 單次票券、scope／revision／到期皆驗證 |
| `COMMERCE_MODE` | `disabled` | 只允許 disabled／simulation，real 拒絕 |
| `DB_CONNECTION` | mysql | 不因方便改 SQLite |
| `CACHE_STORE` | database | 實際 Laravel 版本核對鍵名與必要資料表 |
| `SESSION_DRIVER` | database | 正式 cookie 安全；雙後臺不共用 Session |
| `QUEUE_CONNECTION` | database | worker／失敗任務／重試機制確實存在 |
| `DB_HOST`、`DB_PORT`、`DB_DATABASE`、`DB_USERNAME` | 由環境供應 | Laravel 與 WP 分帳號；root 不給應用 |
| `SESSION_SECURE_COOKIE` | 正式 true | 反向代理 HTTPS 判定同步驗證 |
| `SIMULATION_DATA_RETENTION_DAYS` | 30 | 可調但需記錄理由與清理證據 |
| `CART_RETENTION_DAYS` | 7 | 與 Session／購物車到期行為一致 |
| `DEPLOY_ENVIRONMENT` | staging 或 production | 與簽章、公鑰、volume 互相匹配 |
| `DEPLOY_CHANNEL` | 專案核准名稱 | 不採任意「latest release」 |
| `RELEASE_ID` | 經驗簽清單提供 | 只供部署核對，不當身分憑證 |

`session.upload_progress.enabled=0` 是 PHP 啟動 INI 設定，不是 Laravel `.env` 原生設定。兩個 Web PHP 服務都須讀回確認，並移除公開診斷頁。

正式快取／Session／queue 所需資料表由 migrations 管理；不是設定成 database 就自動存在。改設定鍵或框架版本時，同步驗證 `.env.example`、讀取程式與實際運行值。[S17][S18][S31]

## D.3 秘密目錄

| 秘密類型 | 存放與供應對象 | 輪替注意 |
|---|---|---|
| Laravel `APP_KEY` | 各環境獨立，僅 Laravel 與核准復原流程 | 不在每次重啟生成；評估加密資料影響 |
| Laravel／WP DB 密碼 | 各自 secret file，應用不可互讀對方 DB | 先新增／切換再撤舊，測連線池 |
| MySQL 管理密碼 | 僅初始化／管理工作 | 不掛載給 Web 應用 |
| WP salts | CMS 執行環境 | 輪替會影響登入，記錄維護 |
| WP 服務憑證 | Laravel 受控服務查詢需要時 | 最小權限，不能是管理員登入密碼 |
| 事件 HMAC／預覽簽章資料 | 雙方所需端點、用途分離 | 新舊 key ID 過渡，不能無期限接受舊 key |
| 發布簽章私鑰 | 對應 GitHub environment | staging／production 不共用；主機只拿公鑰 |
| GHCR 拉取憑證 | 常駐主機，必要時唯讀 | 不含 repo 寫入／管理權 |
| 部署狀態唯讀 token | 主機與對應部署 workflow | 不等於網站管理員或 DB 權限 |
| 備份目的地憑證／解密資料 | 主機備份工作＋獨立受控復原保管 | 不能與備份只留同一主機 |
| 管理員與 2FA 復原資料 | 主公核准的安全管道 | 不打印於公開建置 log 或 README |

`*_FILE` 為本案啟動層約定，逐一實作檔案讀取、權限、空值、換行與缺件驗證。缺少正式秘密即拒絕啟動，不能落入固定的示範密碼。

## E.2 里程碑完成報告

每份報告記錄：需求／測試 ID、受測 commit、完成檔案、執行環境、版本清單、命令、成功／失敗／未跑／阻擋數、畫面證據、風險、回復方式與下一個工作項。主公只看短摘要時，仍可點到完整證據。

自動檢查至少包含：

1. 第 12 章全部測試 ID 都出現在測試登錄表；沒有重號、幽靈 ID 或無理由跳過。
2. 新增公開路由均有可見性／授權測試；新增環境鍵均有設定目錄與缺件驗證。
3. 文件說存在的腳本真的存在、可解析且與 `--help` 一致，不是清單佔位。
4. JSON／YAML／Compose／Nginx 與 PHP 基本語法檢查通過；通過語法不冒充功能驗收。
5. `.env.example` 無真實秘密；生成的映像、前端 bundle、repo history 與證據無已知敏感內容。
6. 更新站點後，程式版本與報告 commit 一致；跨會話還原後仍可重跑。
7. 沒有使用 `latest`、虛構 SHA、跳過 TLS 驗證、公開診斷頁或正式測試資料重置。
8. 所有 P0 失敗先修正；外部阻擋明列，不能加上「已完成」的標題掩蓋。

GitHub artifact 保存期間採專案明確設定：例如一般測試 14 天、候選版證據 30 天，屬本案可調設計。較長期只保留去秘密化摘要與核准的稽核證據；不可用 CI artifact 長期保存正式備份。[S15]
