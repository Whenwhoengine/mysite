# 資料清單與保存規則（DAT-01、DAT-03、DAT-06、COM-12）

本文件列出 Laravel 主站（含模擬商店與管理後臺）實際保存的資料：目的、欄位、保存期限、接收者與存取權，以及查詢／刪除申請與還原後重套的流程。

- **保存天數一律是本專案的預設值，不是法定保存年限或法定刪除期限。** 正式上線前，須由網站負責人依當時適用的法規、業別規範與實際資料處理角色重新確認。
- 任何新增欄位、分析服務、追蹤 cookie、電子報或外部資料接收者，都必須**先**更新本清單與隱私告知，才可上線（v5 §16.3）。
- WordPress 內容系統（文章、媒體、編輯帳號、草稿與預覽）的欄位明細由內容工作包維護；本清單第 2 節只列出 Laravel 端會接觸到的部分，WordPress 端的完整明細則補在第 2 節的「2.2 WordPress 端資料明細」。

最後更新：2026-11-05（補齊 WordPress 端與內容整合資料表；前一版：商店與後臺工作包，M5–M7）。

### 本專案**不**收集的資料

- 信用卡號、有效期、CVV、任何付款資訊、銀行帳號：結帳表單沒有這些欄位，伺服器收到這類欄位名稱會直接回 `422 SIMULATION_ONLY` 並拒絕。
- 真實收件地址、電話：同上。測試代號 `buyer_code` 只接受英數字與連字號（最多 20 字），介面提示不得填入個資。
- 訪客 email、姓名：商店不收集；訪客不需要註冊或登入。
- 分析或追蹤 cookie：本工作包未加入任何分析服務。

## 2. 與 WordPress 內容系統相關的資料（由內容工作包補充明細）

### 2.1 本版預設摘要

| 資料類別 | 本版預設（v5 §16.3） | 備註 |
|---|---|---|
| 公開文章與影音中繼資料 | 由網站負責人決定發布與保留 | 作者、照片等仍依實際內容處理權利 |
| 草稿、私人內容與修訂 | 不傳到公開快取或證據檔 | 預覽票券與預覽 Session 的保存規則見內容工作包 |
| WordPress 編輯帳號 | 由 WordPress 管理 | 與 Laravel 後臺帳號**互不相通**，同名或同 email 也不會取得 Laravel 權限 |
| 備份 | 依第 15 章及資料用途限制 | 還原後必須執行第 5 節的重套程序 |

### 2.2 WordPress 端資料明細

- 存放位置：WordPress 專用資料庫 `mysite_wp`（專用帳號 `mysite_wp`，與 Laravel 的 `mysite_app` 分庫分帳號，見 `infra/compose.base.yml`），資料表前綴 `wp_`（`wp/config/wp-config.template.php`）；媒體檔在 Docker volume `wp-uploads`。
- WordPress 帳號與 Laravel 後臺帳號**互不相通**：兩邊各自登入、各自授權，同名或同 email 也不會取得對方的權限。
- 保存期限寫「目前無自動清理（待決定）」的項目，代表程式中查不到刪除或清理作業，需由網站負責人決定期限後再實作。
- 排程依據：wp-jobs 容器（`infra/images/wordpress/jobs.sh`）每 30 秒一輪（`WP_JOBS_INTERVAL_SECONDS`，暫定）執行到期的 WP-Cron 事件與 outbox 投遞，至少間隔 60 秒執行一次 `wp site-content reconcile`；`DISABLE_WP_CRON` 已開啟，不靠訪客觸發。

## 3. 保存期限如何執行

- 排程：`routes/console-commerce.php` 每日 03:17（`APP_TIMEZONE`）執行 `php artisan mysite:retention:apply`；scheduler 由 `app-scheduler` 容器單一實例執行。
- 手動預覽：`php artisan mysite:retention:apply --dry-run` 只計算筆數、不異動資料。
- 作業內容：
  1. 模擬訂單 `placed_at` 超過保存天數且尚未匿名化 → 逐筆匿名化，每筆寫一列 `data_deletion_log`（`subject_type=order`、`action=anonymize`）。匿名化後原訂單網址立即失效。
  2. 稽核紀錄 `created_at` 超過保存天數 → 刪除，寫一列條件式刪除紀錄（`subject_type=audit_logs`、`criteria.created_before`）。
  3. `sessions` 的 `last_activity` 超過購物車保存天數 → 刪除（購物車隨之消失），寫一列條件式刪除紀錄。
- 保存天數的允許範圍由 `App\Support\Config\MysiteConfig` 在啟動時驗證：模擬資料 1–365、購物車 1–90、稽核 7–730 天；沒有「永久保存」的設定值。

## 4. 查詢與刪除申請（DAT-03）

本商店為模擬用途，通常不保存可識別個人的資料；後臺帳號（工作人員 email）與 log 中的 IP 前綴是主要可能涉及個資的部分。收到申請時：

1. **登記與身分確認**：記錄收件日期、申請人、申請類型（查詢／閱覽／複製本，或更正、停止處理、刪除），並以合理方式確認申請人身分。
2. **依申請類型分流期限**：依「當時有效」的個人資料保護法與相關規定處理，不套用單一天數。依 v5 §16.2 所引官方說明（[S46][S47]），**查詢、閱覽或製給複製本**的准駁決定原則為 15 日、**更正、停止處理或刪除**的准駁決定原則為 30 日，延長條件與通知方式依法辦理。上述期限是「作出准駁決定」的期限，不代表所有技術刪除都在同一天完成，也不是可以任意延後的許可。**正式上線前，須由負責人核對條文現行版本與生效狀態，並把核對結果與日期記錄在此。**（待核對）
3. **查找資料**：後臺帳號查 `users`；操作紀錄查 `audit_logs`（以 `actor_user_id` 或 email HMAC `email_hash`）；模擬訂單沒有可識別個人的欄位（測試代號為合成值），通常無資料可提供。
4. **刪除或停止處理**：後臺帳號以「停用」立即停止使用；如需刪除帳號列，先確認稽核保存需求，再由維運者處理並在 `data_deletion_log` 記錄。訂單相關資料可提前執行匿名化。
5. **回覆並保存處理紀錄**（申請日期、決定日期、處理內容），處理紀錄本身不保存不必要的個資。

## 5. 還原備份後重套（DAT-06）

還原任何舊備份後、開放服務之前，執行：

```bash
php artisan mysite:deletion-log:reapply --dry-run   # 先看會處理多少
php artisan mysite:deletion-log:reapply
```

- 已匿名化的訂單若因還原而回到原狀，會再次匿名化；已刪除的稽核紀錄與 Session 依當時記錄的截止條件再次刪除。
- 重套是冪等的：重複執行不會重複處理。
- 若還原的備份比 `data_deletion_log` 本身還舊（刪除紀錄也被倒回），請改從最新備份取得 `data_deletion_log` 表後再重套；之後再執行一次 `mysite:retention:apply` 補上依天數到期的資料。

## 6. 個資事件的內部程序

疑似外洩時：立即限制擴散、保存必要證據（不在證據中複製個資或秘密）、通知指定負責人並查明範圍。對主管機關或當事人的外部通知與時限，由網站負責人依當時適用的法規判斷；本專案**不**把任何單一時數（例如「一律 72 小時」）寫成普遍法定規則。
