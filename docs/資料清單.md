# 資料清單與保存規則（DAT-01、DAT-03、DAT-06、COM-12）

本文件列出 Laravel 主站（含模擬商店與管理後臺）實際保存的資料：目的、欄位、保存期限、接收者與存取權，以及查詢／刪除申請與還原後重套的流程。

- **保存天數一律是本專案的預設值，不是法定保存年限或法定刪除期限。** 正式上線前，須由網站負責人依當時適用的法規、業別規範與實際資料處理角色重新確認。
- 任何新增欄位、分析服務、追蹤 cookie、電子報或外部資料接收者，都必須**先**更新本清單與隱私告知，才可上線（v5 §16.3）。
- WordPress 內容系統（文章、媒體、編輯帳號、草稿與預覽）的欄位明細由內容工作包維護；本清單第 2 節只列出 Laravel 端會接觸到的部分，WordPress 端細節以內容工作包文件為準（待補）。

最後更新：2026-11-05（商店與後臺工作包，M5–M7）。

## 1. Laravel 主站與模擬商店

| 資料類別 | 存放位置 | 目的 | 欄位 | 保存期限（專案預設） | 接收者 | 存取權 |
|---|---|---|---|---|---|---|
| 模擬訂單 | `orders` | 展示模擬下單流程、統計 | 訂單編號、狀態（placed／cancelled）、幣別、小計／總計、件數、建立／取消時間；查詢 token 的 SHA-256、Session 綁定 HMAC、冪等鍵、**可選的合成測試代號** `buyer_code` | `placed_at` 起 **30 天**（`SIMULATION_DATA_RETENTION_DAYS`）後**匿名化**：清除 token hash、Session 綁定、冪等鍵與測試代號；保留金額、件數、狀態與時間供統計 | 無外部接收者 | 訪客：只能以「token＋建立訂單的同一 Session」查看自己的訂單；後臺 admin／viewer 可讀；admin 可取消、匯出 |
| 訂單明細 | `order_items` | 下單當下的價格快照（COM-07） | 商品／規格 ID、商品標題、規格名稱、SKU、單價、數量、小計 | 與訂單相同；匿名化時**保留**（不含個資） | 無 | 同上；建立後不可修改或刪除 |
| 庫存異動 | `inventory_mutations` | 庫存守恆與稽核 | 規格 ID、增減量、異動後庫存、原因、訂單 ID、操作者 ID、備註 | 不自動刪除（不含個資）；備註欄請勿填個資 | 無 | 後臺 admin／viewer 可讀；只追加 |
| 商品與規格 | `products`、`product_variants` | 商店內容 | 代稱、標題、描述、價格、狀態、封面網址、示例標記；SKU、名稱、價格、庫存、啟用 | 由網站負責人決定（封存不刪，保留歷史） | 公開（上架中商品） | admin 可寫、viewer 可讀 |
| 購物車 | Laravel Session（`sessions` 表的 payload） | 暫存訪客選購內容 | 規格 ID、數量、加入時的價格快照（不具計價權威） | 最後異動起 **7 天**（`CART_RETENTION_DAYS`）未活動即清空；Session 本身另受 `SESSION_LIFETIME` 限制，兩者取較短者 | 無 | 只有該訪客自己的 Session |
| 結帳票券與 Session 綁定 | Session payload | 冪等與防止他人讀取訂單（COM-05、COM-09） | 隨機 Session 綁定值、最多 5 組（冪等鍵、訂單 token 明文） | 隨 Session 到期；`sessions` 列 `last_activity` 超過 7 天由保存期限作業刪除 | 無 | 只有該訪客自己的 Session |
| Session（訪客與後臺） | `sessions` | 登入狀態、CSRF、購物車 | Session ID、使用者 ID（後臺）、IP、User-Agent、payload | 同上（7 天未活動刪除；框架另有 lottery 清理） | 無 | 系統內部 |
| 後臺帳號 | `users` | 管理後臺登入 | 名稱、email、密碼雜湊、角色（admin／viewer）、停用時間、2FA 秘密與復原碼（加密）、2FA 確認時間 | 帳號存續期間；停用不刪除（保留稽核對應） | 無 | admin 可在後臺查看清單並停用／啟用；帳號只由維運者以指令建立 |
| 密碼重設 token | `password_reset_tokens` | 重設密碼 | email、token 雜湊、建立時間 | 60 分鐘失效（`auth.passwords.users.expire`） | 郵件捕捉器（見下） | 系統內部 |
| 稽核紀錄 | `audit_logs` | 權限、商品、庫存、訂單、匯出、使用者停用、登入與 2FA 事件的追溯 | 操作者 ID／類型、動作、對象型別與 ID、**去秘密化** metadata、IP 前綴（IPv4 /24、IPv6 /48） | **90 天**（`AUDIT_RETENTION_DAYS`）後刪除 | 無 | 後臺 admin／viewer 可讀；不可修改 |
| 刪除紀錄 | `data_deletion_log` | 還原備份後重套刪除／匿名化（DAT-06） | 對象型別、對象 ID、動作（anonymize／purge）、條件（截止時間）、原因、筆數、執行時間 | 不自動刪除（不含被刪除的內容本身） | 無 | 維運者 |
| 模擬訂單通知 | 郵件捕捉器（`MAIL_MAILER=log` → 應用程式 log） | 驗證「提交後才通知」 | 訂單編號、狀態、件數、金額、明細；**不含** token、Session 綁定或任何個資；收件者固定為保留網域 `simulated-orders@mysite.invalid` | 依應用程式 log 的保存設定（待主機 log 輪替規則確定） | 無（不寄出） | 維運者 |
| 密碼重設信 | 郵件捕捉器（同上） | 正式郵件服務核准前的重設流程 | 收件 email、重設連結（含一次性 token） | 依應用程式 log 的保存設定；token 60 分鐘失效、用過即失效 | 無（不寄出） | 維運者 |
| 應用程式 log | 容器 stderr（JSON） | 故障排除 | 事件、request ID、錯誤碼；已遮罩 token、密碼、cookie 等 | 依主機／容器 log 輪替（待查，見 runbook） | 無 | 維運者 |
| 快取與佇列 | `cache`、`jobs`、`failed_jobs` | 效能與背景工作 | 依各功能；不放訂單 token 或密碼 | 快取依 TTL；失敗工作由維運者清理 | 無 | 系統內部 |

### 本專案**不**收集的資料

- 信用卡號、有效期、CVV、任何付款資訊、銀行帳號：結帳表單沒有這些欄位，伺服器收到這類欄位名稱會直接回 `422 SIMULATION_ONLY` 並拒絕。
- 真實收件地址、電話：同上。測試代號 `buyer_code` 只接受英數字與連字號（最多 20 字），介面提示不得填入個資。
- 訪客 email、姓名：商店不收集；訪客不需要註冊或登入。
- 分析或追蹤 cookie：本工作包未加入任何分析服務。

## 2. 與 WordPress 內容系統相關的資料（由內容工作包補充明細）

| 資料類別 | 本版預設（v5 §16.3） | 備註 |
|---|---|---|
| 公開文章與影音中繼資料 | 由網站負責人決定發布與保留 | 作者、照片等仍依實際內容處理權利 |
| 草稿、私人內容與修訂 | 不傳到公開快取或證據檔 | 預覽票券與預覽 Session 的保存規則見內容工作包 |
| WordPress 編輯帳號 | 由 WordPress 管理 | 與 Laravel 後臺帳號**互不相通**，同名或同 email 也不會取得 Laravel 權限 |
| 備份 | 依第 15 章及資料用途限制 | 還原後必須執行第 5 節的重套程序 |

## 3. 保存期限如何執行

- 排程：`routes/console-commerce.php` 每日 03:17（`APP_TIMEZONE`）執行 `php artisan mysite:retention:apply`；scheduler 由 `app-scheduler` 容器單一實例執行。
- 手動預覽：`php artisan mysite:retention:apply --dry-run` 只計算筆數、不異動資料。
- 作業內容：
  1. 模擬訂單 `placed_at` 超過保存天數且尚未匿名化 → 逐筆匿名化，每筆寫一列 `data_deletion_log`（`subject_type=order`、`action=anonymize`）。匿名化後原訂單網址立即失效。
  2. 稽核紀錄 `created_at` 超過保存天數 → 刪除，寫一列條件式刪除紀錄（`subject_type=audit_logs`、`criteria.created_before`）。
  3. `sessions` 的 `last_activity` 超過購物車保存天數 → 刪除（購物車隨之消失），寫一列條件式刪除紀錄。
- 保存天數的允許範圍由 `App\Support\Config\MysiteConfig` 在啟動時驗證：模擬資料 1–365、購物車 1–90、稽核 7–730 天；沒有「永久保存」的設定值。

## 4. 查詢與刪除申請（DAT-03）

本商店為模擬用途，通常不保存可識別個人的資料；後臺帳號（工作人員 email）與 log 中的 IP 前綴是主要可能涉及個資的部分。收到申請時：

1. **登記與身分確認**：記錄收件日期、申請人、申請類型（查詢／閱覽／複製本，或更正、停止處理、刪除），並以合理方式確認申請人身分。
2. **依申請類型分流期限**：依「當時有效」的個人資料保護法與相關規定處理，不套用單一天數。依 v5 §16.2 所引官方說明（[S46][S47]），**查詢、閱覽或製給複製本**的准駁決定原則為 15 日、**更正、停止處理或刪除**的准駁決定原則為 30 日，延長條件與通知方式依法辦理。上述期限是「作出准駁決定」的期限，不代表所有技術刪除都在同一天完成，也不是可以任意延後的許可。**正式上線前，須由負責人核對條文現行版本與生效狀態，並把核對結果與日期記錄在此。**（待核對）
3. **查找資料**：後臺帳號查 `users`；操作紀錄查 `audit_logs`（以 `actor_user_id` 或 email HMAC `email_hash`）；模擬訂單沒有可識別個人的欄位（測試代號為合成值），通常無資料可提供。
4. **刪除或停止處理**：後臺帳號以「停用」立即停止使用；如需刪除帳號列，先確認稽核保存需求，再由維運者處理並在 `data_deletion_log` 記錄。訂單相關資料可提前執行匿名化。
5. **回覆並保存處理紀錄**（申請日期、決定日期、處理內容），處理紀錄本身不保存不必要的個資。

## 5. 還原備份後重套（DAT-06）

還原任何舊備份後、開放服務之前，執行：

```bash
php artisan mysite:deletion-log:reapply --dry-run   # 先看會處理多少
php artisan mysite:deletion-log:reapply
```

- 已匿名化的訂單若因還原而回到原狀，會再次匿名化；已刪除的稽核紀錄與 Session 依當時記錄的截止條件再次刪除。
- 重套是冪等的：重複執行不會重複處理。
- 若還原的備份比 `data_deletion_log` 本身還舊（刪除紀錄也被倒回），請改從最新備份取得 `data_deletion_log` 表後再重套；之後再執行一次 `mysite:retention:apply` 補上依天數到期的資料。

## 6. 個資事件的內部程序

疑似外洩時：立即限制擴散、保存必要證據（不在證據中複製個資或秘密）、通知指定負責人並查明範圍。對主管機關或當事人的外部通知與時限，由網站負責人依當時適用的法規判斷；本專案**不**把任何單一時數（例如「一律 72 小時」）寫成普遍法定規則。
