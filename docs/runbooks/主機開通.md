# 主機開通手冊（P0–P8）

> 對應：規劃書 v5 §13.3–13.7、執行契約 §14.2／§14.6。全部操作都在**雲端供應商的瀏覽器主控臺**（web console／serial console）與 **GitHub 網頁設定**完成；不需要也不提供本機 SSH、Windows 或 WSL 步驟。
> 本手冊只描述程序；主機、網域、備份目的地與核准紀錄尚未提供前，對應步驟一律記為 `BLOCKED_EXTERNAL`，不得宣稱完成。

## 0. 名詞與路徑

| 名稱 | 說明 |
|---|---|
| 平台程式 | 本儲存庫某個**已審核 commit** 的唯讀副本，放在 `/srv/mysite/platform` |
| 環境目錄 | `/srv/mysite/environments/<staging|production>/{config,secrets,releases,state}` |
| TLS | `/srv/mysite/tls/letsencrypt`（憑證，0700）、`/srv/mysite/tls/acme`（ACME webroot） |
| 備份暫存 | `/srv/mysite/backup-staging/<env>`（0700，成功或失敗後都會清除本次 dump） |
| 核准參照 | 例如 `approval-2026-11-20-host`：委託人核准紀錄的識別字串，所有開通命令都要帶 `--approved-plan=` |

staging 與 production 建議分主機；若暫放同一主機，兩者的 Compose project、資料庫、volume、秘密、備份前綴、網域與簽章金鑰都必須不同（腳本已依環境名稱自動分開）。

## P0　核准與範圍

1. 確認主機帳戶、月費上限、區域、維護者名單；記錄在核准紀錄（不寫密碼、付款卡號）。
2. 決定主站與 CMS 兩個主機名稱（例如 `www.<網域>`、`cms.<網域>`），不得覆寫其他網站或郵件用的 DNS 紀錄。
3. 產出核准參照字串，後續每一步沿用。

成功證據：核准紀錄連結。未取得：`BLOCKED_EXTERNAL: HOST_NOT_PROVISIONED`。

## P1　建立主機

1. 在供應商主控臺建立 Linux VPS：Docker 官方支援的 **Ubuntu 24.04 LTS（x86_64）**，起始 2 vCPU／4 GB RAM／可擴充 SSD（工程估算，需實測）。
2. 記錄資源 ID、區域、對外 IP；不要把 root 密碼寫進任何文件。
3. 供應商防火牆先只開 **80、443**（主控臺管理不需要對外開 SSH）。

## P2　取得已審核的平台程式

在供應商的**瀏覽器主控臺**登入後執行（`<COMMIT>` 換成核准紀錄上的完整 commit SHA）：

```bash
sudo -i
apt-get update && apt-get install -y git jq python3 openssl ca-certificates curl bzip2
install -d -m 0755 /srv/mysite
git clone https://github.com/Whenwhoengine/mysite /srv/mysite/platform
git -C /srv/mysite/platform checkout --detach <COMMIT>
git -C /srv/mysite/platform rev-parse HEAD     # 必須等於核准的 COMMIT
```

不要使用 `curl … | sh` 之類未審查的遠端管線。之後每次升級平台程式，同樣以「核准 commit → checkout → 核對 SHA」進行。

## P3　安裝 Docker 與建立目錄

1. 依 Docker 官方文件〈Install Docker Engine on Ubuntu〉的 apt repository 方式安裝 `docker-ce`、`docker-ce-cli`、`containerd.io`、`docker-compose-plugin`（以當日官方頁面為準，不憑記憶貼指令）。
2. 先做唯讀檢查，再正式建立：

```bash
cd /srv/mysite/platform
bash scripts/deploy/bootstrap-host.sh --env=staging --approved-plan=<核准參照> --check-only
bash scripts/deploy/bootstrap-host.sh --env=staging --approved-plan=<核准參照> --install-restic
```

腳本會：檢查 OS／Docker（Engine ≥ 25.0、Compose ≥ 2.24，暫定下限）→ 建立目錄與權限 → 建立 `config/deploy.env` 範本 → **只補缺**產生應用秘密（DB 密碼、APP_KEY、WP salts、事件／預覽金鑰、部署狀態權杖、內部 CA；不輸出、不覆寫）→ 安裝 systemd unit／timer → 依 `infra/versions.env`（或已查核的預設值）下載 restic 並核對 SHA-256。
3. 重開機一次，確認 `systemctl is-active docker` 為 active。

## P4　秘密與 GitHub 設定

**主機端（主控臺）**

1. 編輯 `/srv/mysite/environments/staging/config/deploy.env`：填 `APP_HOST`、`CMS_HOST`、`ACME_EMAIL`、`ADMIN_EMAIL`。鍵名與格式由 `scripts/lib/deploy.sh` 的白名單驗證，未知鍵會被拒絕。
2. 備份密碼與目的地**先存進委託人的受控保管處（密碼管理器）**，再寫入主機；不要讓解密資料只存在這台主機：

```bash
E=/srv/mysite/environments/staging/secrets
read -rs -p '貼上 restic 密碼：' v; printf '%s' "$v" > "$E/restic_password"; unset v; echo
read -r  -p '貼上 restic repository（例如 s3:https://…/mysite-staging）：' v; printf '%s' "$v" > "$E/restic_repository"; unset v
chmod 0640 "$E/restic_password" "$E/restic_repository"; chgrp 33 "$E/restic_password" "$E/restic_repository"
```

   雲端儲存憑證（只限 `AWS_*`、`B2_*`、`AZURE_*`、`GOOGLE_*` 白名單鍵）寫入 `restic_env`（每行 `KEY=VALUE`，0640）。之後初始化 repository（只需一次）：

```bash
( set -a; . "$E/restic_env" 2>/dev/null; set +a
  RESTIC_PASSWORD_FILE="$E/restic_password" RESTIC_REPOSITORY_FILE="$E/restic_repository" /usr/local/bin/restic init )
```

3. GHCR：套件若為公開可略過；若為私人，建立只有 `read:packages` 的權杖寫入 `secrets/ghcr_pull_token`，並在 `deploy.env` 設 `GHCR_AUTH=token`、`GHCR_USERNAME=<帳號>`。

**簽章金鑰（每個環境一把，不共用）**：在主控臺的記憶體目錄產生，複製到 GitHub 後立即銷毀主機副本（主機只保存公鑰）：

```bash
umask 077; openssl genpkey -algorithm ED25519 -out /dev/shm/staging-2026a.pem
openssl pkey -in /dev/shm/staging-2026a.pem -pubout -out /root/staging-2026a.pub.pem
cat /dev/shm/staging-2026a.pem        # 複製到 GitHub environment secret 與委託人的受控保管處
shred -u /dev/shm/staging-2026a.pem
cat /root/staging-2026a.pub.pem       # 公鑰（非秘密）
```

**GitHub 網頁（Settings → Environments／Variables）**

| 位置 | 名稱 | 內容 |
|---|---|---|
| environment `staging`（production 另設，且必須設 required reviewers） | secret `RELEASE_SIGNING_KEY_ED25519` | 上面的私鑰 PEM |
| 同上 | secret `DEPLOY_STATUS_TOKEN` | 主機 `secrets/deploy_status_token` 的內容（在主控臺 `cat` 後貼上） |
| 同上 | variable `RELEASE_SIGNING_KEY_ID` | `staging-2026a`（必須以環境名稱開頭） |
| 同上 | variables `APP_HOST`、`CMS_HOST` | 核准主機名稱 |
| repository variables | `RELEASE_PUBLIC_KEY_STAGING`、`RELEASE_PUBLIC_KEY_PRODUCTION` | 公鑰 PEM（非秘密） |

不要把任何秘密貼進聊天、issue、PR 或 Git。

## P5　安裝驗簽公鑰並驗證

```bash
bash scripts/deploy/bootstrap-host.sh --env=staging --approved-plan=<核准參照> --trust-key=staging-2026a:/root/staging-2026a.pub.pem
rm -f /root/staging-2026a.pub.pem
bash scripts/deploy/preflight.sh --env=staging
```

- 同一 key_id 已存在但內容不同會被拒絕；金鑰輪替一律用新 key_id（見《秘密輪替》）。
- 假簽章測試：任何用其他私鑰簽的清單都會在 `verify-release.sh` 得到 `BAD_SIGNATURE`／`UNKNOWN_KEY_ID`（自動化測試 M02／M03 已涵蓋，主機上可再以 `pull-release.sh --dry-run` 驗證 channel）。

## P6　DNS、HTTP 驗證入口與 HTTPS

1. DNS：核對既有紀錄 → 建立核准子網域的 A 紀錄（IPv6 全鏈路可用才加 AAAA）→ 從外部查詢確認解析。
2. 首次只開 ACME＋維護頁（不引用尚不存在的憑證）：

```bash
bash scripts/deploy/bootstrap-host.sh --env=staging --approved-plan=<核准參照> --start-edge
```

3. 先以 Let’s Encrypt 測試環境演練（`deploy.env` 設 `ACME_SERVER=staging`），成功後改回 `production` 再申請正式憑證：

```bash
bash scripts/deploy/bootstrap-host.sh --env=staging --approved-plan=<核准參照> --issue-tls
```

   失敗時維護頁保持不變，不得以自簽憑證充數。成功後 `MYSITE_GATEWAY_MODE` 自動改為 `https`。
4. 外部掃描確認只有 80／443 對外（Docker 發布的 port 可能繞過 UFW，必須以外部掃描實測）。
5. 續期：`mysite-certbot-renew.timer` 每日兩次；演練 `bash infra/systemd/libexec/mysite-certbot-renew.sh --dry-run`（OPS-13）。
6. HSTS 在所有正式子網域與 HTTPS 行為確認後才設定 `MYSITE_HSTS_HEADER=max-age=…`；首輪不加 includeSubDomains／preload。

## P7　備份與告警

1. 確認 P4 的 restic 秘密已就緒後重跑 bootstrap（會啟用備份 timer）：`mysite-backup-app@staging.timer`（每小時）、`mysite-backup-wp@staging.timer`（每日）、`mysite-backup-check@staging.timer`（每週抽樣讀回）。
2. 手動測一次：`bash scripts/ops/backup.sh --env=staging --reason=manual-first`，確認 `state/backups.jsonl` 有 snapshot ID。
3. 告警：目前以 systemd unit 失敗狀態（`systemctl --failed`、`journalctl -u 'mysite-*'`）呈現；送達核准通道（OPS-10）需委託人核准通道與憑證，未提供前為 `BLOCKED_EXTERNAL: BLK-ALERT-01`。

## P8　staging 首次部署、重開機與還原演練

1. GitHub：main 的 commit 通過 `ci` 後，`release` workflow 產生候選版；在 Actions 手動執行 `deploy-staging`（填 release run ID 與 schema 分類）。
2. 主機：首次安裝需要明確核准，timer 自動拉取會停在 `FIRST_INSTALL_APPROVAL_REQUIRED`。在主控臺：

```bash
bash scripts/deploy/pull-release.sh --env=staging --dry-run          # 取得並驗證，存到 releases/verified/
bash scripts/deploy/release.sh --env=staging \
  --verified-envelope=/srv/mysite/environments/staging/releases/verified/seq-1.envelope.json \
  --first-install-approved=<核准參照>
```

   WordPress 管理員初始密碼在 `secrets/wp_admin_password`，只經核准安全管道交付，不印入 log。
3. 重開機驗證（OPS-08）：重開後確認容器自動恢復、timer 仍啟用、資料仍在。
4. 還原演練：`bash scripts/ops/restore-check.sh --env=staging --snapshot=latest --target=isolated --level=full`（見《備份與還原》）。
5. 全部通過後才能申請 production（重複 P1–P8，用 production 自己的金鑰、秘密、網域與備份前綴）。
