# 秘密輪替手冊

> 對應：規劃書 v5 §13.7、附錄 D.3；設定目錄 `docs/設定目錄.md`。每次輪替都需要核准參照（`--approved-plan=`），新值只寫入秘密檔（0640、群組 33），**從不輸出**；紀錄只含種類、階段、時間與結果（`state/rotations.jsonl`）。
> 輪替與部署互斥（共用部署鎖），進行中會看到 `LOCK_BUSY`。

## 1. 一般命令

```bash
cd /srv/mysite/platform
bash scripts/ops/rotate-secrets.sh --env=production --kind=<種類> --approved-plan=<核准參照> [--phase=<階段>]
```

development 也可用，但必須明示：`--env=development --allow-development`（作用於 `.runtime/secrets/development` 與 `mysite-dev`）。
testing 同理：`--env=testing --allow-testing`（作用於 `.runtime/secrets/testing` 與 `mysite-test`）。

## 2. 各種類

| 種類 | 程序（腳本自動分段） | 失敗時 | 影響 |
|---|---|---|---|
| `app-db`／`wp-db` | 確認目前密碼可登入 → `ALTER USER … RETAIN CURRENT PASSWORD`（新舊都可登入）→ 換秘密檔 → 重建相關容器 → 以新密碼登入＋應用健康檢查 → `DISCARD OLD PASSWORD` | 原密碼設回主要並撤銷新密碼、秘密檔與容器回原狀（exit 50 `VERIFY_FAILED_REVERTED`） | 容器重建期間短暫中斷 |
| `wp-salts` | 換 8 組 salts → 重建 wp-php／wp-jobs → 驗證；上一組保留供 `--phase=revert` | 自動回到原 salts | **所有 WP 登入失效**，需事先公告 |
| `wp-service` | 先發行新 Application Password → 換秘密檔 → 重建 Laravel → 以新密碼呼叫 WP `users/me` 實測 → 撤銷舊密碼 | 刪除新密碼、回到原值 | 無（雙期） |
| `event-hmac`／`preview` | `--phase=add`（新 key 只被接受）→ `promote`（新 key 簽章，舊 key 仍接受）→ `retire`（撤舊）；每階段先重建接收端（Laravel）再重建發送端（WP），並確認兩端實際載入的金鑰圈與秘密檔一致 | 回到上一階段；`--phase=revert` 可手動回退 | 無（雙期） |
| `app-key` | `--phase=add`（新 APP_KEY，舊 key 移入 `app_previous_keys`）→ 觀察期 → `--phase=retire` | 回到原 APP_KEY | Laravel 以舊 key 解密既有資料與 Session |

前提（未滿足時腳本 exit 20 `APP_SUPPORT_MISSING`，不做任何變更）：

- `event-hmac`／`preview`：應用程式須支援金鑰圈檔（`content_event_hmac_keyring`、`preview_signing_keyring`，每行 `<key_id> <64 hex> <active|accept>`），並在主機設定 `KEYRING_SUPPORT=yes`。目前應用只讀單一金鑰，屬待整合項目。
- `app-key`：Laravel 須支援 `APP_PREVIOUS_KEYS_FILE`，主機設定 `APP_PREVIOUS_KEYS_SUPPORT=yes`。

> 2026-11-05 更新（GAP-KEYRING-01 已解決）：上列「目前應用只讀單一金鑰」已不再成立。Laravel 與 WordPress 都已支援金鑰圈，Laravel 也支援 `APP_PREVIOUS_KEYS_FILE`；`KEYRING_SUPPORT`、`APP_PREVIOUS_KEYS_SUPPORT` 預設改為 `yes`（`scripts/lib/deploy.sh`）。主機若仍在執行金鑰圈支援之前的發布，請在 `config/deploy.env` 明確寫 `KEYRING_SUPPORT=no`、`APP_PREVIOUS_KEYS_SUPPORT=no`，輪替就會以 exit 20 拒絕。即使設定為 `yes`，腳本每期也會以 `php artisan mysite:keyring` 與 `wp site-content keyring`（app-php、wp-php、wp-jobs）確認實際載入的內容；映像過舊而不一致時視為驗證失敗並回到上一階段（exit 50 `VERIFY_FAILED_REVERTED`）。

## 2.1 事件 HMAC／預覽簽章：金鑰圈三期與期限

金鑰圈檔在秘密目錄內（`content_event_hmac_keyring`、`preview_signing_keyring`），每行 `<key_id> <64 hex> <active|accept>`，恰好一把 `active`。首次 bootstrap 由既有單一金鑰建立 `k1 <金鑰> active`。

| 階段 | 金鑰圈（以 k1→k2 為例） | 發送端（WP）簽章 | 接收端（Laravel／WP 預覽驗證）接受 |
|---|---|---|---|
| 開始 | `k1 active` | k1 | k1 |
| `--phase=add` | `k1 active`、`k2 accept` | k1 | k1、k2 |
| `--phase=promote` | `k1 accept`、`k2 active` | k2 | k1、k2 |
| `--phase=retire` | `k2 active` | k2 | 只有 k2（以 k1 簽的事件→401、票券→403） |

- 期限（暫定值，待實測調整）：promote 之後**至少 15 分鐘**（預覽票券硬上限 900 秒，讓 promote 前核發的票券自然過期）、**最多 24 小時**內必須執行 `--phase=retire`。舊 key 只在 retire 之前被接受，retire 把它移出金鑰圈，不會無期限接受舊 key。promote 成功時腳本會印出並在 `state/rotations.jsonl` 記錄 retire 期限。
- add 之後確認腳本回報成功（兩端已載入新金鑰圈）再 promote；add 與 promote 之間沒有安全上的期限（新 key 只被接受、尚未簽章），但不宜擱置。
- 事件 outbox 每次重試都以當下的 active key 重新簽章，所以 promote 之後的重試會自動改用新 key；retire 之後若有以舊 key 送達失敗而進死信的事件，修好後以 `wp site-content outbox replay <event_id>` 重播即會以新 key 簽章。
- retire 時，單一金鑰檔（`content_event_hmac_key`／`preview_signing_key`）也同步為剩下的 active key，日後即使改回單一金鑰模式也不會回到已撤銷的舊 key。不要刪除金鑰圈檔來「回到單一金鑰」。
- 疑似外洩：add → promote 後立即 retire（跳過觀察期），代價是 promote 前核發、尚未使用的預覽票券失效（編輯重新按預覽即可）。
- 確認目前狀態（不輸出金鑰）：`php artisan mysite:keyring event-hmac`、`wp site-content keyring event-hmac`（預覽改 `preview`）；兩者輸出必須與秘密檔的 `<key_id> <狀態>` 一致。

## 2.2 APP_KEY：add → retire

- `--phase=add`：舊 APP_KEY 移入 `app_previous_keys`（Laravel 原生 `APP_PREVIOUS_KEYS`／`config('app.previous_keys')`），換上新 APP_KEY；新資料一律以新 key 加密，舊資料與 Session 仍可以舊 key 解密。腳本以 `php artisan mysite:keyring app-key` 確認 Laravel 實際載入的舊金鑰數量。
- 觀察期內把需要長期保存的加密資料重新加密（若有），再執行 `--phase=retire` 清空 `app_previous_keys`（檔案保留為空檔，Compose 需要它存在）。retire 之後以舊 key 加密的資料與 Session 無法再解密。

## 3. 不在腳本範圍、需人工依序進行的輪替

**發布簽章金鑰（雙期信任）**
1. 依《主機開通》P4 產生新金鑰（新 key_id，例如 `production-2027a`），私鑰存入 GitHub environment secret 與受控保管處，主機副本銷毀。
2. 主機：`bootstrap-host.sh --env=production --approved-plan=<參照> --trust-key=production-2027a:<公鑰檔>`（新舊公鑰並存）。
3. GitHub：更新 `RELEASE_SIGNING_KEY_ED25519`、`RELEASE_SIGNING_KEY_ID`、repository variable `RELEASE_PUBLIC_KEY_PRODUCTION`。
4. 以新金鑰完成一次部署並確認後，刪除主機上的舊公鑰檔 `config/trusted-keys/<舊 key_id>.pem`（撤銷演練：以舊金鑰簽的清單應得到 `UNKNOWN_KEY_ID`）。
疑似外洩時跳過觀察期：先 `touch state/channel-paused`，直接移除舊公鑰，再依《事故處理》檢查已發布 digest。

**部署狀態唯讀權杖（`deploy_status_token`）**：產生新值寫入秘密檔（`openssl rand -hex 32 > …`，0640、群組 33）→ 重建 app-php、app-worker、app-scheduler → 更新 GitHub environment secret `DEPLOY_STATUS_TOKEN` → 下一次部署 workflow 驗證可讀。

**restic 密碼**：`restic key add`（新密碼先存入受控保管處）→ 換 `secrets/restic_password` → 手動備份一次成功 → `restic key list` 確認後 `restic key remove <舊 key ID>`。

**MySQL root 密碼**：只供初始化與管理；以 `ALTER USER 'root'@'%'`（及 `'root'@'localhost'`）配合秘密檔更新，完成後驗證 `rotate-secrets.sh` 的 DB 種類仍可執行。

**GHCR 唯讀權杖、GitHub 唯讀權杖**：先在 GitHub 建立新權杖（最小權限）→ 換秘密檔 → `pull-release.sh --dry-run` 驗證 → 撤銷舊權杖。

## 4. 紀錄與檢查

- `state/rotations.jsonl`：種類、階段、核准參照、結果。
- `secrets/.rotation/`（0700）只在輪替進行中或雙期觀察期保存上一組值，成功或 retire 後清除；不得複製到其他位置。
- 輪替後執行 `bash scripts/deploy/preflight.sh --env=<env>` 確認秘密檔權限與服務狀態。
