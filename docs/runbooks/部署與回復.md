# 部署與回復手冊

> 對應：規劃書 v5 §14.1–14.8、§15.5；OPS-03～OPS-06、OPS-11。命令介面以各腳本 `--help` 為準。
> 「清單上傳成功」只代表發布申請完成；主機回報相同 release ID 且外部 HTTPS 冒煙通過，才算部署成功。

## 1. 整體流程

```text
main 已通過 ci 的 commit
  → release.yml：scripts/lib/build.sh 建置 → Trivy 掃描（HIGH／CRITICAL 已有修補即阻擋）→ 推 GHCR → 候選版 artifact（digest＋來源 commit）
  → deploy-staging.yml（environment: staging）：分配新序號 → 簽署 → 上傳 channel-staging 的 release-envelope.json＋不可變紀錄 deploy-staging-seq-N
  → staging 主機 mysite-pull-release@staging.timer（約每 5 分鐘）：取得 → 驗證 → release.sh
  → workflow 輪詢 https://<APP_HOST>/internal/deploy-status（DEPLOY_STATUS_TOKEN）→ 公開 HTTPS 冒煙
  → deploy-production.yml（environment: production，需核准）：只接受 channel-staging 目前的同一批 digest，不重建、不重新 resolve
```

主機端 `release.sh` 的固定順序：

| 步驟 | 內容 | 失敗時 |
|---|---|---|
| 1 | 重新驗證清單（驗簽→schema→環境／channel→序號→時效） | exit 40，不動服務 |
| 2 | `flock` 部署鎖 | exit 50 `LOCK_BUSY`（另一部署進行中） |
| 3 | pending 持久化；同一清單重試上限 `RELEASE_MAX_ATTEMPTS`（預設 3，暫定） | exit 50 `RETRY_LIMIT_EXCEEDED`，需新序號清單 |
| 4 | 磁碟容量（`MIN_FREE_DISK_MB`，預設 3072，暫定）、https 模式憑證存在 | exit 20 |
| 5 | 拉齊 5 個應用映像＋平台 MySQL 映像，逐一核對 digest | exit 50／40，不動服務 |
| 6 | 部署前備份（`backup.sh --scope=all`）；確實空環境才以空環境證據代替 | exit 50 `BACKUP_FAILED`，不動服務 |
| 7 | schema 判斷：`none`／`expand` 自動；`contract`／`breaking` 需 `--approved-schema-plan` 等於清單 `migration_plan_ref` | exit 40 `SCHEMA_APPROVAL_REQUIRED`，不動服務 |
| 8 | 暫停寫入者（worker、scheduler、wp-jobs）；`contract`／`breaking` 另 `artisan down` | — |
| 9 | 新映像一次性容器：`php artisan migrate --force`、`wp core update-db`、`wp site-content setup` | none／expand：舊版恢復服務；其他：維持維護待人工 |
| 10 | 換版：新 app-php → `artisan up` → 全部服務 `up -d --wait`（worker／scheduler 隨新映像重建，scheduler 單一實例） | none／expand 自動回到上一版程式 |
| 11 | `smoke.sh`：容器內與經 gateway 讀 `/internal/deploy-status`、主站 `/healthz`、CMS health、http→https | 不符→回到上一版（exit 30）；逾時→`DEPLOYMENT_UNCONFIRMED`（exit 50，不記成功） |
| 12 | 記錄 active、寫入 `state/history.jsonl` | — |

部署從不執行 `down -v`、`migrate:fresh`、`migrate:rollback`、全域 prune 或資料還原。

## 2. 常用命令（主控臺，於 `/srv/mysite/platform`）

```bash
bash scripts/deploy/preflight.sh --env=staging                          # 前置檢查（不部署）
bash scripts/deploy/pull-release.sh --env=staging --dry-run             # 取得並驗證 channel，不部署
bash scripts/deploy/verify-release.sh --env=staging --envelope=<檔> --json
bash scripts/deploy/release.sh --env=staging --verified-envelope=<檔> [--approved-schema-plan=<參照>]
bash scripts/deploy/rollback.sh --env=staging --approved-release=<回復清單>
bash scripts/deploy/smoke.sh --env=staging --expected-release=<release_id> [--external]
python3 -I scripts/lib/manifest.py state-get --state-dir /srv/mysite/environments/staging/state --environment staging --field active
journalctl -u mysite-pull-release@staging.service -n 100
```

狀態檔（受限權限，不含秘密）：`state/release-state.json`（active／pending／最高已接受序號）、`state/history.jsonl`、`state/events.jsonl`、`state/smoke-last.json`、`releases/seq-N.*`。

## 3. 狀況判讀

| 主機訊息 | 意義 | 處置 |
|---|---|---|
| `NOOP` | 相同序號且內容相同的清單已成功套用 | 無需處理 |
| `REPLAY_OLD_SEQUENCE`／`SEQUENCE_REUSED` | 重播或序號被其他內容使用 | 檢查 channel 是否被人工改動；重新走 deploy workflow 取得新序號 |
| `BAD_SIGNATURE`／`UNKNOWN_KEY_ID` | 簽章或金鑰不符 | 視為安全事件（見《事故處理》），先暫停 channel |
| `EXPIRED` | 清單超過有效期（24 小時） | 重新執行 deploy workflow 產生新序號清單 |
| `SCHEMA_APPROVAL_REQUIRED` | contract／breaking 尚未核准 | 取得核准後在主控臺執行 `release.sh … --approved-schema-plan=<與 migration_plan_ref 相同>` |
| `FIRST_INSTALL_APPROVAL_REQUIRED` | 空環境首次安裝 | 見《主機開通》P8 |
| `BACKUP_FAILED` | 部署前備份失敗，未換版 | 依《備份與還原》排除後讓 timer 重試或手動重跑 |
| `RETRY_LIMIT_EXCEEDED` | 同一清單已失敗 3 次 | 查 `events.jsonl` 原因、修正後以新序號重新發布 |
| `DEPLOYMENT_UNCONFIRMED` | 已換版但未能確認 | 不記成功；人工以 `smoke.sh` 與外部 HTTPS 核對，必要時回復 |
| `SMOKE_FAILED_REVERTED` | 新版不符，已回到上一版程式 | 修正後重新發布 |
| `*_HOLD` | 無法自動回復，現場保留 | 依下表決策，必要時維護模式＋核准方案 |

## 4. 回復決策表（v5 §15.5）

| 問題 | 優先處理 | 禁止 |
|---|---|---|
| 新版程式錯，schema 向後相容 | 以 deploy workflow 填 `rollback_target_release=<舊 release_id>`、release run 選舊候選版，產生**新序號**回復清單；主機 `rollback.sh` 只換 digest | 回到已撤銷（`config/revoked-digests.txt`）或已知有漏洞的版本 |
| schema 變更不相容 | 維護模式、保護新寫入、依已審核方案向前修正或受控還原 | 自動 `migrate:rollback` |
| 部分模擬訂單已新增 | 先保留／比對新增資料，必要時經核准補償 | 用舊 DB 覆寫導致訂單消失 |
| 媒體誤刪 | 從對應 snapshot 選擇性還原檔案（見《備份與還原》） | 為一張圖整庫倒帶 |
| 正式主機故障 | 新主機依《主機開通》＋備份重建，確認後切 DNS | 把開發 VM 當正式站 |
| 發布私鑰疑似外洩 | `touch state/channel-paused` 停止採用 channel、輪替信任金鑰、檢查已發布 digest | 信任後續同一私鑰簽出的清單 |

`rollback.sh` 只接受：新的更大序號、目標 release 曾在本主機成功啟用、images 與當時紀錄完全相同、目標之後只有 none／expand 變更、digest 未撤銷。它會先備份，但**不跑 migration、不還原資料**。「回復程式」與「資料還原到舊時間點」是不同操作；後者必須另行授權，不藏在部署命令裡。

production 的程式回復可略過「與 channel-staging 相同 digest」檢查（因主機會核對目標曾在 production 成功啟用），其他情況 production 只能部署 staging 目前的同一批 digest。
