# 部署與回復手冊

> 對應：規劃書 v5 §14.1–14.8、§15.5；OPS-03～OPS-06、OPS-11。命令介面以各腳本 `--help` 為準。
> 「清單上傳成功」只代表發布申請完成；主機回報相同 release ID 且外部 HTTPS 冒煙通過，才算部署成功。

## 1. 整體流程

```text
main 已通過 ci 的 commit
  → release.yml：scripts/lib/build.sh 建置 → Trivy 掃描（HIGH／CRITICAL 已有修補即阻擋）→ 推 GHCR → 候選版 artifact（digest＋來源 commit）
  → deploy-staging.yml（environment: staging）：分配新序號 → 簽署 → 上傳 channel-staging 的 release-envelope.json＋不可變紀錄 deploy-staging-seq-N
  → staging 主機 mysite-pull-release@staging.timer（約每 5 分鐘）：取得 → 驗證 → release.sh
  → workflow 輪詢 https://<APP_HOST>/internal/deploy-status（DEPLOY_STATUS_TOKEN）→ 公開 HTTPS 冒煙
  → deploy-production.yml（environment: production，需核准）：只接受 channel-staging 目前的同一批 digest，不重建、不重新 resolve
```

- release.yml 的「main CI 成功後自動執行」預設關閉：推送 GHCR 會佔用 GitHub Packages 儲存額度，私有套件超出免費額度可能計費。確認費用與套件可見性後，到 repo 的 Settings → Secrets and variables → Actions → Variables 新增 `MYSITE_AUTO_RELEASE=true` 才會自動執行；在 main 上手動觸發（workflow_dispatch）不受此開關影響。

主機端 `release.sh` 的固定順序：

| 步驟 | 內容 | 失敗時 |
|---|---|---|
| 1 | 重新驗證清單（驗簽→schema→環境／channel→序號→時效） | exit 40，不動服務 |
| 2 | `flock` 部署鎖 | exit 50 `LOCK_BUSY`（另一部署進行中） |
| 3 | pending 持久化；同一清單重試上限 `RELEASE_MAX_ATTEMPTS`（預設 3，暫定） | exit 50 `RETRY_LIMIT_EXCEEDED`，需新序號清單 |
| 4 | 磁碟容量（`MIN_FREE_DISK_MB`，預設 3072，暫定）、https 模式憑證存在 | exit 20 |
| 5 | 拉齊 5 個應用映像＋平台 MySQL 映像，逐一核對 digest | exit 50／40，不動服務 |
| 6 | 部署前備份（`backup.sh --scope=all`）；確實空環境才以空環境證據代替 | exit 50 `BACKUP_FAILED`，不動服務 |
| 7 | schema 判斷：`none`／`expand` 自動；`contract`／`breaking` 需 `--approved-schema-plan` 等於清單 `migration_plan_ref` | exit 40 `SCHEMA_APPROVAL_REQUIRED`，不動服務 |
| 8 | 暫停寫入者（worker、scheduler、wp-jobs）；`contract`／`breaking` 另 `artisan down`，並同時開啟 CMS 維護模式（`wp site-content maintenance on`，見第 5 節） | CMS 無法進維護：exit 50 `WP_MAINTENANCE_FAILED`，Laravel 解除維護、不換版 |
| 9 | 新映像一次性容器：`php artisan migrate --force`、`wp core update-db`、`wp site-content setup` | none／expand：舊版恢復服務；其他：維持維護待人工 |
| 10 | 換版：新 app-php → `artisan up` → 全部服務 `up -d --wait`（worker／scheduler 隨新映像重建，scheduler 單一實例）→ 新版 wp-php 就緒後關閉 CMS 維護模式（只在第 8 步有開啟時） | none／expand 自動回到上一版程式；CMS 無法退出維護：exit 50 `WP_MAINTENANCE_OFF_FAILED`（不進 smoke、不記成功） |
| 11 | `smoke.sh`：容器內與經 gateway 讀 `/internal/deploy-status`、主站 `/healthz`、CMS health、http→https | 不符→回到上一版（exit 30）；逾時→`DEPLOYMENT_UNCONFIRMED`（exit 50，不記成功） |
| 12 | 記錄 active、寫入 `state/history.jsonl` | — |

部署從不執行 `down -v`、`migrate:fresh`、`migrate:rollback`、全域 prune 或資料還原。

## 2. 常用命令（主控臺，於 `/srv/mysite/platform`）

```bash
bash scripts/deploy/preflight.sh --env=staging                          # 前置檢查（不部署）
bash scripts/deploy/pull-release.sh --env=staging --dry-run             # 取得並驗證 channel，不部署
bash scripts/deploy/verify-release.sh --env=staging --envelope=<檔> --json
bash scripts/deploy/release.sh --env=staging --verified-envelope=<檔> [--approved-schema-plan=<參照>]
bash scripts/deploy/rollback.sh --env=staging --approved-release=<回復清單>
bash scripts/deploy/smoke.sh --env=staging --expected-release=<release_id> [--external]
python3 -I scripts/lib/manifest.py state-get --state-dir /srv/mysite/environments/staging/state --environment staging --field active
journalctl -u mysite-pull-release@staging.service -n 100
```

狀態檔（受限權限，不含秘密）：`state/release-state.json`（active／pending／最高已接受序號）、`state/history.jsonl`、`state/events.jsonl`、`state/smoke-last.json`、`releases/seq-N.*`。

## 3. 狀況判讀

| 主機訊息 | 意義 | 處置 |
|---|---|---|
| `NOOP` | 相同序號且內容相同的清單已成功套用 | 無需處理 |
| `REPLAY_OLD_SEQUENCE`／`SEQUENCE_REUSED` | 重播或序號被其他內容使用 | 檢查 channel 是否被人工改動；重新走 deploy workflow 取得新序號 |
| `BAD_SIGNATURE`／`UNKNOWN_KEY_ID` | 簽章或金鑰不符 | 視為安全事件（見《事故處理》），先暫停 channel |
| `EXPIRED` | 清單超過有效期（24 小時） | 重新執行 deploy workflow 產生新序號清單 |
| `SCHEMA_APPROVAL_REQUIRED` | contract／breaking 尚未核准（pending 狀態 `awaiting_approval`；timer 不會自動重試，以免耗盡重試次數） | 取得核准後在主控臺執行 `release.sh … --verified-envelope=releases/verified/seq-N.envelope.json --approved-schema-plan=<與 migration_plan_ref 相同>` |
| `FIRST_INSTALL_APPROVAL_REQUIRED` | 空環境首次安裝 | 見《主機開通》P8 |
| `BACKUP_FAILED` | 部署前備份失敗，未換版 | 依《備份與還原》排除後讓 timer 重試或手動重跑 |
| `RETRY_LIMIT_EXCEEDED` | 同一清單已失敗 3 次 | 查 `events.jsonl` 原因、修正後以新序號重新發布 |
| `DEPLOYMENT_UNCONFIRMED` | 已換版但未能確認 | 不記成功；人工以 `smoke.sh` 與外部 HTTPS 核對，必要時回復 |
| `SMOKE_FAILED_REVERTED` | 新版不符，已回到上一版程式 | 修正後重新發布 |
| `*_HOLD` | 無法自動回復，現場保留 | 依下表決策，必要時維護模式＋核准方案 |
| `WP_MAINTENANCE_FAILED` | contract／breaking 部署時 CMS 無法進入維護模式（例如 wp-php 異常，或現行版本還沒有維護模式指令） | 已讓舊版恢復服務、未換版；以第 5 節確認 `wp site-content maintenance status` 可用後重跑 |
| `WP_MAINTENANCE_OFF_FAILED` | 已換版，但 CMS 無法退出維護模式（CMS 仍擋寫入，公開讀取照常） | 不記成功；查 wp-php 狀態並以 `smoke.sh` 核對新版，再依第 5 節手動 `maintenance off`；要讓主機記錄 active，以同一清單重跑 `release.sh`（受重試上限限制） |

## 4. 回復決策表（v5 §15.5）

| 問題 | 優先處理 | 禁止 |
|---|---|---|
| 新版程式錯，schema 向後相容 | 以 deploy workflow 填 `rollback_target_release=<舊 release_id>`、release run 選舊候選版，產生**新序號**回復清單；主機 `rollback.sh` 只換 digest | 回到已撤銷（`config/revoked-digests.txt`）或已知有漏洞的版本 |
| schema 變更不相容 | 維護模式、保護新寫入、依已審核方案向前修正或受控還原 | 自動 `migrate:rollback` |
| 部分模擬訂單已新增 | 先保留／比對新增資料，必要時經核准補償 | 用舊 DB 覆寫導致訂單消失 |
| 媒體誤刪 | 從對應 snapshot 選擇性還原檔案（見《備份與還原》） | 為一張圖整庫倒帶 |
| 正式主機故障 | 新主機依《主機開通》＋備份重建，確認後切 DNS | 把開發 VM 當正式站 |
| 發布私鑰疑似外洩 | `touch state/channel-paused` 停止採用 channel、輪替信任金鑰、檢查已發布 digest | 信任後續同一私鑰簽出的清單 |

`rollback.sh` 只接受：新的更大序號、目標 release 曾在本主機成功啟用、images 與當時紀錄完全相同、目標之後只有 none／expand 變更、digest 未撤銷。它會先備份，但**不跑 migration、不還原資料**。「回復程式」與「資料還原到舊時間點」是不同操作；後者必須另行授權，不藏在部署命令裡。

production 的程式回復可略過「與 channel-staging 相同 digest」檢查（因主機會核對目標曾在 production 成功啟用），其他情況 production 只能部署 staging 目前的同一批 digest。

## 5. 維護模式（主站與 CMS）

對應 v5 §14.7 第 5、7 步；CMS 維護模式解決 GAP-CMS-MAINT-01。

### 5.1 什麼時候開、什麼時候關

| 情況 | 主站（Laravel `artisan down`） | CMS（`wp site-content maintenance`） |
|---|---|---|
| `none`／`expand` 變更 | 不進維護（舊版在 migration 期間繼續服務） | 不進維護 |
| `contract`／`breaking`（已核准） | 第 8 步開啟；第 10 步新 app-php 就緒後 `artisan up` | 第 8 步緊接 `artisan down` 開啟（早於暫停寫入者與 migration）；第 10 步全部服務以新版就緒後關閉（避免舊版 WP 程式對已變更的 schema 寫入），之後才進 smoke |
| migration 前失敗（MySQL 未就緒、意外錯誤等，舊版恢復服務） | 解除 | 解除 |
| `contract`／`breaking` 的 migration／WP setup 失敗 | 維持維護待人工 | 維持維護待人工 |
| smoke 失敗且無法自動回到上一版（`SMOKE_FAILED_HOLD`；contract／breaking 一定走這條） | 重新進維護 | 重新進維護 |

`release.sh` 記錄的原因格式為 `release seq-<序號> <schema 分類>`。

### 5.2 CMS 維護模式做了什麼

- 狀態存在 WordPress 資料庫（option `site_content_maintenance`），wp-php 與 wp-jobs 讀同一份；只記開始／結束時間（UTC）與原因，不記操作者。
- wp-admin（含 `admin-ajax.php`、`admin-post.php`、`async-upload.php`）對所有登入者只顯示維護說明（HTTP 503＋`Retry-After: 60`），**管理員也一樣**。
- REST 的 POST／PUT／PATCH／DELETE（核心 `/wp/v2/*`、`/batch/v1`、`site-content/v1`，含 `_method` 改寫）一律 503＋`Retry-After`，回應 `code` 為 `site_content_maintenance`、附正體中文說明。
- 照常運作：公開 GET（主站讀取的 `site-content/v1`、health）、主站首頁、私有預覽讀取（GET）、登入頁（會提示維護中；登入後只看到維護說明）。
- wp-jobs：到期排程（`wp cron event run --due-now`）、outbox 投遞與對帳整輪暫停並以 exit 0 結束（心跳照常，健康檢查不受影響）；直接請求 `wp-cron.php` 也不執行排程。維護結束後下一輪（約 30 秒）自動補上，排程發布會延到維護結束後才發生。
- WP-CLI 是維運者的受控通道，不受限制（`wp core update-db`、`wp site-content setup`、手動 `wp cron event run <hook>` 等照常）。outbox 投遞與對帳若在維護中確實要執行，加 `--ignore-maintenance`。

### 5.3 手動開關與確認

開發環境：

```bash
bash scripts/cloud/dev.sh wp site-content maintenance status                 # 文字狀態；加 --format=json 取 JSON
bash scripts/cloud/dev.sh wp site-content maintenance on --reason="手動維護：說明原因"
bash scripts/cloud/dev.sh wp site-content maintenance off
```

staging／production 主控臺（以 production 為例；staging 把 project 換成 `mysite-staging`）：

```bash
wp_php="$(docker ps -q --filter label=com.docker.compose.project=mysite-production --filter label=com.docker.compose.service=wp-php | head -n 1)"
docker exec -u www-data "$wp_php" wp site-content maintenance status
docker exec -u www-data "$wp_php" wp site-content maintenance on --reason="手動維護：說明原因"
docker exec -u www-data "$wp_php" wp site-content maintenance off
```

- 原因最多 200 字，**不要填姓名、email、電話**（含 `@` 會被拒絕，exit 10）。已開啟時再執行 `on` 不會改變開始時間與原因；已關閉時 `off` 不做任何事。
- 開啟後確認：`status` 顯示「維護模式：開啟」；`curl -s -o /dev/null -w '%{http_code}\n' -X POST https://<CMS_HOST>/wp-json/wp/v2/posts` 回 503，`curl -s -o /dev/null -w '%{http_code}\n' https://<CMS_HOST>/wp-json/site-content/v1/health` 回 200，主站首頁回 200。
- 關閉後確認：`status` 顯示「維護模式：關閉（上次 … 開始、… 結束）」；同一個 POST 改回 401（未登入）；編輯者可以正常進入後臺。
- 手動維護（例如受控還原）時，主站是否同時 `artisan down` 由維運者依狀況決定；`release.sh` 結束時會關閉 CMS 維護模式，手動維護期間不要同時執行 contract／breaking 發布。
- 契約測試 `tests/contracts/wp/run.sh --only=maintenance` 會短暫開啟再關閉 CMS 維護模式；若測試被中斷，請以 `status` 確認並手動 `off`。
