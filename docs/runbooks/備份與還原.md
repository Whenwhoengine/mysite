# 備份與還原演練手冊

> 對應：規劃書 v5 第 15 章；OPS-07、DAT-06。目標（非保證）：內容 RPO 24 小時、模擬訂單 RPO 1 小時、主站 RTO 4 小時。
> 沒有備份目的地與解密資料時，正式備份與還原驗收一律為 `BLOCKED_EXTERNAL: BLK-BACKUP-01`。

## 1. 備份內容與一致性

`scripts/ops/backup.sh --env=<env> --reason=<原因> --scope=<all|wp|app>`：

| 內容 | 方法 |
|---|---|
| WordPress DB | MySQL 容器內以 `mysite_wp` 帳號 `mysqldump --single-transaction --routines --triggers --no-tablespaces --hex-blob`，dump 結尾必須有 `-- Dump completed` |
| Laravel DB | 同上，`mysite_app` 帳號 |
| 刪除／匿名化紀錄 | `data_deletion_log` 另存 `db/deletion-log.sql`（還原舊備份時以最新一份重套，DAT-06） |
| WP 媒體 | wp-php 容器內 `tar` 打包 uploads |
| 部署狀態 | `release-state.json`、`history.jsonl`、`compose.env`、主機設定、信任公鑰（皆非秘密） |
| manifest | `backup-manifest.json`：每個檔案大小與 SHA-256、各庫資料表數與筆數估計、備份前後一致時的文章狀態筆數 |

密碼與目的地只以檔案提供（`secrets/restic_password`、`restic_repository`、選用 `restic_env`）。restic `backup` 完成後執行 `restic check`（每週 timer 另加 `--read-data-subset=10%`），並抽回 `backup-manifest.json` 比對，**全部通過才**寫入 `state/backups.jsonl`；紀錄只含 snapshot ID、時間、大小、筆數，不含 dump 內容。

秘密（APP_KEY、WP salts、整合金鑰）**不在**這份備份中：它們必須另存於委託人的受控保管處；沒有解密資料的加密備份不算可用。

## 2. 排程與保留

| timer | 時間（UTC） | scope | 保留（restic forget，限本環境 host＋scope） |
|---|---|---|---|
| `mysite-backup-app@<env>.timer` | 每小時 :17 | app | 小時備 48、日備 30 |
| `mysite-backup-wp@<env>.timer` | 每日 19:27（台北 03:27） | wp | 日備 30、月備 12 |
| `mysite-backup-check@<env>.timer` | 每週六 20:41 | all（deep 檢查） | 日備 30 |
| 部署／回復前 | 由 `release.sh`／`rollback.sh` 觸發 | all | 日備 30 |

保留策略預設只**預覽**（`BACKUP_RETENTION_MODE=preview`，`forget --dry-run`）；確認不會誤刪其他專案資料後，委託人核准才改 `apply`（`forget --prune`）。最近一次有效備份過舊時，以 `state/last-backup-<scope>.json` 的時間判斷並告警。

## 3. 還原演練（每月抽樣、每季完整）

```bash
cd /srv/mysite/platform
bash scripts/ops/restore-check.sh --env=staging --snapshot=latest --target=isolated --level=full
bash scripts/ops/restore-check.sh --env=production --snapshot=<snapshot ID> --target=isolated --level=db --tmpfs-mb=2048
```

- `--target` 只接受 `isolated`；`staging`、`production` 或任何其他值一律 exit 40。
- 每次建立全新 project `mysite-restorecheck-<8 位隨機>`，隨機密碼的 MySQL **不接任何網路**（`--network none`），不寄信、不打 callback、不被索引；結束後以 project label 精確清除容器、volume、網路與暫存。
- `--snapshot=latest` 會取 WP（scope wp／all）與 Laravel（scope app／all）各自最新的 snapshot；指定 ID 則只還原該 snapshot。不論哪一種，都會載入**最新**的刪除紀錄。
- 檢查：完整性（SHA-256）、匯入、已發布／未公開文章數、各狀態筆數與備份當下一致（未公開不會變公開）、媒體引用都在 uploads 中、訂單／商品／庫存表可讀、刪除紀錄筆數。
- `--level=full` 另以還原當時的 Laravel 映像在內部網路執行 `php artisan mysite:deletion-log:reapply`（DAT-06）；`--level=db` 不啟動 Laravel，結果會註明重套 NOT_RUN。
- HTTP 層的「匿名讀不到草稿」、登入、排程與 queue 重新啟動，需在 staging 完整演練時以瀏覽器／E2E 驗證並記錄（目前為人工步驟）。
- 結果寫入 `state/restore-checks.jsonl`：開始／結束時間、實測 RTO、RPO（距 snapshot 時間）、各檢查判定。第一次演練未過，M9 不得 PASS。

## 4. 選擇性還原（需另行授權）

正式資料還原到舊時間點可能造成資料損失，**不屬於**部署或演練命令。確有需要時：先 `backup.sh --reason=before-manual-restore` 保存現況 → 於隔離目錄取回檔案 → 由核准者決定匯入範圍。例：只取回一個媒體檔：

```bash
E=/srv/mysite/environments/production/secrets
RESTIC_PASSWORD_FILE=$E/restic_password RESTIC_REPOSITORY_FILE=$E/restic_repository \
  /usr/local/bin/restic dump <snapshot ID> /srv/mysite/backup-staging/production/snapshot-wp/uploads.tar > /root/uploads.tar
tar -xf /root/uploads.tar -C /root/restore-media ./2026/11/<檔名>
```

再經 WordPress 後臺或受控 `docker cp` 放回，並驗證文章引用。還原 DB 後一定要重套最新刪除紀錄（`php artisan mysite:deletion-log:reapply`），避免已刪除或匿名化的個資復活。
