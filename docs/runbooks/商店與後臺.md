# 模擬商店與管理後臺：操作與故障手冊

適用範圍：Laravel 主站的模擬商店（`/shop`、`/cart`、`/checkout`、`/orders/{token}`）與管理後臺（`/admin`）。商店**只有模擬模式**：不收款、不出貨，不收卡號、真實地址或電話。

以下指令在開發環境以 `bash scripts/cloud/dev.sh artisan <參數>` 執行；正式主機以部署工具提供的 artisan 入口執行（以 `www-data` 身分）。

---

## 1. 商店開關（COMMERCE_MODE）

| 值 | 前臺商店 | 後臺 | 說明 |
|---|---|---|---|
| `disabled`（預設） | 所有商店頁面與寫入回 `404 COMMERCE_DISABLED` | 可登入、可準備商品 | 上線前與一般狀態 |
| `simulation` | 開放；每個結帳／訂單畫面都顯示「模擬操作，不收款、不出貨」 | 同左 | 展示或測試模擬流程 |
| `real` 或其他值 | — | — | 啟動時 `MysiteConfig` 直接拒絕；即使執行期被改成 `real`，商店也只回 `422 SIMULATION_ONLY` |

變更方式：修改環境設定 `COMMERCE_MODE` 後重新建立 app 容器（設定由環境變數讀入，不在後臺切換）。

## 2. 建立管理員（無公開註冊）

帳號只能用指令建立；密碼**只從檔案讀**，不接受命令列明文（避免進入 shell history 與行程列表）。不存在任何固定示範帳密。

```bash
# 在 app 容器內：建立只有自己可讀的暫存密碼檔（至少 12 字元、最多 72 bytes）
umask 077 && cat > /tmp/admin-pw      # 貼上密碼後按 Ctrl-D
php artisan mysite:admin:create --email=you@example.com --name=站長 --role=admin --password-file=/tmp/admin-pw
rm -f /tmp/admin-pw
```

- 帳號已存在 → 印出 `no-op`，**不會**重設密碼或角色。
- `--role=viewer` 建立唯讀人員。
- 建立後登入 `/admin/login`，到「帳號安全」完成 2FA 登記並離線保存復原碼。**staging／production 未完成 2FA 的帳號只能進入「帳號安全」頁。**
- 指令會寫一筆 `admin.user_created` 稽核（不含密碼）。

## 3. 權限矩陣

| 動作 | admin | viewer | 無角色帳號（例如同 email 的其他帳號） | 未登入 |
|---|---|---|---|---|
| 檢視儀表板、商品、訂單、稽核、使用者清單 | ✓ | ✓ | 403 | 導向 `/admin/login` |
| 新增／編輯商品與規格、調整庫存 | ✓ | 403 | 403 | 導向登入 |
| 取消訂單（回補庫存一次） | ✓ | 403 | 403 | 導向登入 |
| 匯出訂單 CSV（留稽核、不含 token） | ✓ | 403 | 403 | 導向登入 |
| 停用／啟用其他帳號（不可停用自己） | ✓ | 403 | 403 | 導向登入 |
| 2FA、更新自己的密碼 | ✓ | ✓ | — | — |

權限在伺服器端以 policies（`app/Policies`）判斷；介面隱藏按鈕只是輔助。WordPress 帳號與 Laravel 帳號互不相通。

## 4. 日常操作

- **停用帳號**：後臺「使用者」→ 停用。立即生效：該帳號所有 Session 被刪除，下次請求即被登出；之後無法登入或重設密碼。
- **忘記密碼**：`/admin/forgot-password`。不論 email 是否存在都顯示同一訊息。正式郵件服務核准前 `MAIL_MAILER=log`，重設信只寫入應用程式 log（`docker compose logs app-php` 可見）；連結 60 分鐘失效、用過即失效。注意：這表示重設連結會出現在 log 中，見第 9 節。
- **商品**：後臺「商品」。價格只接受十進位字串（例如 `350` 或 `350.50`），不接受指數或負數；封面必須是 https 網址或站內路徑。商品改價**不會**改動既有訂單明細。商品不刪除，改用「已封存」。
- **庫存調整**：在商品編輯頁輸入增減數量（例如 `+5`、`-2`）與備註；調整後不得為負。每次調整寫入只追加的 `inventory_mutations` 與稽核。備註請勿填個資。
- **取消訂單**：後臺訂單詳情 → 取消。重複送出不會重複回補（狀態機＋資料庫唯一約束）。已匿名化的訂單不可變更。
- **示例資料**（只限 development／testing）：`php artisan db:seed --class='Database\Seeders\DevelopmentSeeder'`。可重跑、不重設庫存、不建立帳號；含一件只剩 1 件庫存的「示例：限量一件測試品」。

## 5. 保存期限與刪除紀錄

- 每日排程：`mysite:retention:apply`（03:17，`APP_TIMEZONE`）。確認排程：`php artisan schedule:list` 應看到 `commerce-retention`。
- 預覽：`php artisan mysite:retention:apply --dry-run`。
- 還原備份後必做：`php artisan mysite:deletion-log:reapply`（先加 `--dry-run` 檢視）。細節見 `docs/資料清單.md` 第 3、5 節。

## 6. 錯誤碼與故障判斷

| 現象 | 可能原因 | 處理 |
|---|---|---|
| 商店頁 `404`，JSON `COMMERCE_DISABLED` | `COMMERCE_MODE=disabled`（預設） | 確認環境設定；後臺不受影響 |
| `422 SIMULATION_ONLY` | 請求含卡號／付款／地址／電話欄位，或打到 `/checkout/payment`，或模式不是 simulation | 預期行為：本案沒有真實金流 |
| `429 RATE_LIMITED` | 超過限流（見第 8 節暫定值） | 稍後再試；持續發生時檢查是否有異常流量 |
| `419` 頁面已逾時 | CSRF token 不符或 Session 過期 | 重新整理頁面；若所有表單都 419，檢查 Session cookie 與 `SESSION_SECURE_COOKIE`／HTTPS 設定 |
| 訂單網址 `404` | token 錯誤、不是建立訂單的同一瀏覽器 Session、Session 已過期，或訂單已匿名化 | 預期行為（不區分原因，避免被拿來探測）；後臺仍可依訂單編號查詢 |
| 結帳後回到購物車並顯示「庫存不足」 | 送出時庫存已被買走 | 整筆不成立、沒有半張訂單；調整數量再送 |
| 結帳後回到結帳頁並顯示「價格已更新」 | 商品在您檢視後改價 | 確認新價格後再送出 |
| 後臺一直被導回「帳號安全」 | staging／production 未完成 2FA | 完成 2FA 登記 |
| 登入一直失敗 | 密碼錯、帳號停用、帳號沒有角色（訊息刻意相同） | 查 `audit_logs` 的 `auth.login_failed`（只有 email 的 HMAC，不含 email 原文） |

追查順序：先看回應的 `request_id` → `docker compose logs app-php | grep <request_id>` → 稽核紀錄（後臺「稽核紀錄」或 `audit_logs`）。

## 7. 測試

```bash
bash scripts/cloud/dev.sh test --db=commerce tests/Unit/Commerce tests/Feature/Commerce tests/Feature/Admin
bash scripts/cloud/dev.sh test --db=commerce tests/Integration/Commerce   # 真實 MySQL 多程序併發
```

- 併發測試（`tests/Integration/Commerce`，`#[Group('concurrency')]`）以 `proc_open` 啟動多個獨立 PHP 程序（`bin/commerce-worker.php`），各自連線 MySQL、同時搶同一批庫存列；不使用 RefreshDatabase，自行建立與清理資料，且只在 `mysite_app_test_*` 測試庫執行。涵蓋：最後一件搶購、持鎖下不超賣、多品項固定鎖序、同冪等鍵並發重送、跨 Session 同鍵、提交前故意失敗、真實 InnoDB 死鎖與重試、並發取消只回補一次。
- 覆蓋率：在 tools 容器以 `php -d pcov.enabled=1 vendor/bin/phpunit --coverage-clover ...` 執行。

## 8. 暫定值（待實測調整）

| 名稱 | 暫定值 | 位置 |
|---|---|---|
| 登入限流 | 每 email＋IP 每分鐘 5 次 | `FortifyServiceProvider` |
| 2FA 挑戰限流 | 每個待驗證登入每分鐘 5 次 | `FortifyServiceProvider` |
| Fortify 路由整體限流 | 每 IP 每分鐘 60 次 | `FortifyServiceProvider` |
| 登入失敗最短耗時 | 250ms | `AuthenticateAdminUser` |
| 購物車寫入限流 | 每 Session＋IP 每分鐘 60 次 | `CommerceServiceProvider` |
| 結帳／取消限流 | 每 Session＋IP 每分鐘 10 次；每 IP 每分鐘 30 次 | `CommerceServiceProvider` |
| 後臺寫入限流 | 每使用者每分鐘 30 次 | `CommerceServiceProvider` |
| 後臺匯出限流 | 每使用者每分鐘 5 次 | `CommerceServiceProvider` |
| 交易死鎖重試 | 最多 3 次，每次退避 10–40ms × 次數 | `TransactionRunner` |
| 每個 Session 保留的結帳票券 | 5 組 | `CommerceSession` |
| 管理帳號密碼長度 | 至少 12 字元、最多 72 bytes | `PasswordValidationRules`、`CreateAdminUser` |
| 儀表板低庫存提示 | ≤ 3 件 | `DashboardController` |
| 保存期限排程時間 | 每日 03:17 | `routes/console-commerce.php` |

已有設定鍵的上限（不在此表）：每項數量上限 `commerce.max_line_quantity`（10）、行數上限 `commerce.max_cart_lines`（20）、保存天數（見 `docs/設定目錄.md`）。

## 9. 已知限制與待辦

- 正式郵件服務尚未核准：重設密碼與模擬訂單通知都只寫入 log 捕捉器，不宣稱已寄達。重設連結含一次性 token，會出現在應用程式 log；建議整合者把 `MAIL_LOG_CHANNEL` 指向權限較嚴、保存較短的獨立 log 通道。
- 訂單 token 明文只保存在訪客自己的 Session payload（`orders` 表只存 SHA-256）。若 `SESSION_DRIVER=database`，建議正式環境開啟 `SESSION_ENCRYPT=true`。
- 訪客訂單只在建立訂單的同一 Session 內可查；Session 到期後只能由後臺依訂單編號查詢。
