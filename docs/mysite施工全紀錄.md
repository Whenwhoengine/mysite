## 3. 第一階段：mysite 網站主體（M0～M8，2026-11-05）

- **架構**：WordPress 只管內容（文章、影片、Podcast、頁面）；Laravel 13 負責公開網站、模擬商店與管理後臺。兩邊只透過 REST API 與簽章事件溝通；MySQL 8.4 分資料庫、分帳號。全部用 Docker Compose 在雲端 Linux 建置與測試，委託人的電腦只用瀏覽器。
- **安全設計**：秘密只放在不進版本控制的檔案；HTML 只經一個安全元件輸出；預覽票券與事件都要簽章；商店預設關閉、不收真實金流。
- **測試與證據**：每次 CI 在全新的環境從零建置，結果存成證據檔匯入儲存庫；驗收登錄表逐項記錄通過、失敗或外部阻擋。
- **合併**：PR #1（`aad927e`，網站主體）、PR #2（`98bd557`，簽章金鑰圈、CMS 維護模式、排程補救、只信任 gateway 固定位址）。
- 詳細內容見 `docs/mysite建置總結v1.md`、`docs/交付報告v2.md`。

## 4. 第二階段：gateway 登入限流修補（PR #4，2026-11-07）

- 問題：最前面的 gateway 只比對精確的登入網址，`/admin/login/`（多一個斜線）和 `/index.php/admin/login` 可以繞過登入次數限制（Laravel 自己的限制仍有效）。
- 修正：限流規則接受結尾斜線、`/index.php/` 開頭一律回 404；新增 doctor 檢查 GW-LOGIN-LIMIT 與部署工具檢查 S07。另修好全新開發環境安裝 PHP 套件失敗的問題。
- 合併：PR #4（`27b6662`）。

## 5. 第三階段：React 前端專案（2026-11-06～07）

依《MySiteReact前端專案定案執行》（優先）、v2、v1 施工。目標：公開頁改由 Next.js 呈現，畫面由委託人用 MyDyad 設計；WordPress 與 Laravel 照舊。

### 5.1 F0～F2（mysite PR #3）
- **F0**：三份計畫書逐位元組收進 `docs/`；新增 ADR-015；舊文件中受影響的段落加修訂註記（原文不刪），並以雜湊守門防止原文被改。
- **F1 公開 API 契約**：12 個端點的 OpenAPI 契約、有效 54 個與無效 16 個樣本、畫面欄位對照表、DOM 測試掛鉤清單。
- **F2 Laravel 公開唯讀 API**：`/api/v1/*` 只接受 GET、不帶 cookie、錯誤一律回 JSON；對外一律 404，只給內部前端用；假資料匯出指令供前端預覽。
- **兩輪查錯**：每輪兩位獨立審查員。修好 `/index.php/api/…` 可繞過 gateway 的漏洞、關閉框架預設的 CORS 等；每項修正都做金絲雀（故意改壞，確認測試變紅，再復原）。
- **與 PR #4 的衝突**：兩邊都改了 gateway 範本與 doctor。只用合併（不改寫歷史），登入規則採 PR #4 的新版，`/index.php/` 阻擋只留一條。
- **合併**：PR #3（`a1d540e`）。

### 5.2 D13 數值（委託人「使持節決行」授權施工者定值）
- 搜尋限流：每個 IP 每分鐘 30 次（與 Laravel 現行限制相同）。
- 前端呼叫 API 的逾時：50000 毫秒（依實測與算式，必須小於 gateway 的 60 秒）。
- 兩張新的內部網路 `frontend`、`frontend-api`。
- 其餘三項（API 總量上限、前端記憶體、設計工具 CPU）要等 F6 實測。

### 5.3 F3 前端骨架（MySiteStorage PR #1）
- Next.js 16.4.5（Pages Router，伺服器渲染）、React 19.3.1、Tailwind CSS 4.3.5、TypeScript 5.9.3、Playwright 1.63.0。
- 資料層有真資料、假資料兩種模式；任何連線失敗、逾時、格式不符都顯示 503 錯誤頁；正式環境不准用假資料。
- 受保護元件（HTML 輸出、YouTube、Podcast、圖片、錯誤頁等）與設計區分開：設計區只有 `src/views`、`src/components`（`safe/` 除外）、`src/styles`、`public/design`，其他一律受保護。
- 第一版外觀複刻現有 Blade 網站，三種寬度並排比對一致。
- **受保護路徑守門**：每個對 main 的合併請求都會檢查改了哪些檔。設計分支改到受保護檔就擋下並附還原指令；施工者分支必須在說明裡逐一列出改到的受保護檔。判定邏輯 171 項單元測試、工作流程 18 個模擬情境（含惡意字串不會被執行）。
- **程式審查後的修正**：2 項中等（站內換頁會帶走上一頁的播放器與選單狀態；有好幾種寫法可以繞過「HTML 只能從一處輸出」的規定）與 13 項輕微（以真的 PHP 8.5.12 與執行中的 Blade 網站逐項比對：頁碼上限、陣列型網址參數、405、標題截斷寬度、錯誤訊息等），全部修好。
- **合併**：PR #1（`ed20bcc`）。

### 5.4 守門實測（FE-11）與設定
- 委託人在 MySiteStorage 建立事件政策 `protected-paths-guard`（只允許守門這一支檔案使用 `pull_request_target`），施工者以截圖讀回。
- 施工者開 5 個測試合併請求（#2～#6）實測：設計分支只改設計區 → 通過；改到受保護檔、改到 `.github/`、把設計區檔案改名移出 → 擋下並附還原指令；施工者分支沒宣告 → 擋下；只改說明補上宣告 → 自動重判並通過；多列、少列 → 擋下；推新提交後舊結果不算。測完全部關閉，沒有合併。
- 委託人設定前端 main 的必要檢查（`frontend-ci`、`protected-paths`）；施工者重開一個會被擋的測試請求，GitHub 判定「無法合併」。
- 「他人 fork」這一案無法用單一帳號實測，由單元測試與模擬涵蓋。
- 設計分支 `design/work` 已更新到最新的 main，可以開始設計。

## 8. 現在已經生效的保護

- 兩個儲存庫的 main 都有分支保護，合併前必須通過指定的自動測試，管理員也不能繞過：mysite 三項（靜態檢查與秘密掃描、整合驗證 content、整合驗證 simulation），前端兩項（`frontend-ci`、`protected-paths`）。
- 前端設計分支改到不該改的檔案會被守門擋下，留言附還原指令。
- 前端只允許守門這一支檔案使用 `pull_request_target`，GitHub 12 月 2 日起的預設阻擋不影響它。
- 所有建置用的外部檔案都以雜湊固定，內容一變就拒絕使用。
