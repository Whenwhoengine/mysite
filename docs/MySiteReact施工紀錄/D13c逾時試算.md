## 0. 結論

1. **WordPress 單次呼叫最壞 W＝10.1 秒**（第一次嘗試 5 秒＋重試間隔 0.1 秒＋第二次嘗試 5 秒）。程式語意與 §4.8、§3.3 查核 6 一致；程式本身也以 `worstCaseSeconds()` 算出 10.1，且有測試與 CI 證據（§1）。
2. **現行實作對 WordPress 的呼叫全部依序**，沒有任何並行（§2 末）。
3. **site 部分（主選單、頁尾選單、站台資訊）冷快取時依序 3 次＝30.3 秒＋L_site**，本身就比列表、單篇、搜尋、分類指定型別這幾類內容端點慢（§4）。
4. **最壞頁型是分類總覽與標籤總覽（未帶 `type`）：依序 4 次＝40.4 秒＋L**。首頁若內容端點沿用現行 `home` 動作內的 `/site` 呼叫，也是 4 次（§3）。
5. **最壞資料等待＝max(30.3＋L_site, 40.4＋L_x) 秒**；當 L_x＋10.1 ≥ L_site 時即為 40.4＋L_x。
6. **前端逾時下限＝max(30.3＋L_site, 40.4＋L_x)＋J**（前端逾時須大於此值；J 為 JSON 解析與驗證時間）。
7. **距 gateway 60 秒上限：60－40.4＝19.6 秒**，這段要容納 L_x、J、前端畫面產生 R 與各段網路開銷。
8. 附帶發現（僅列出，未動手）：現行 Blade 模式的首頁（6 次＝60.6 秒＋L）與分類／標籤總覽（7 次＝70.7 秒＋L），在 WordPress「每次都慢、但最後成功」時，整頁最壞已超過 60 秒（附錄 A）。

## 1. 單次呼叫最壞耗時：程式語意查核

### 1.1 參數與出處

| 項目 | 現行值 | 出處 |
|---|---|---|
| 連線逾時 `connect_timeout` | 2 秒 | `app/config/mysite.php:27`；`infra/compose.base.yml:49`；`docs/設定目錄.md:24`；套用於 `app/app/Domain/Content/Http/WordPressRestClient.php:145` |
| 每次嘗試的總時限 `timeout` | 5 秒（每次嘗試各自受限） | `app/config/mysite.php:28`；`infra/compose.base.yml:50`；`docs/設定目錄.md:25`；套用於 `WordPressRestClient.php:146-147`；註解見同檔第 21 行 |
| 最多嘗試次數 | 2（設定寫死 2，程式再夾在 1～2） | `app/config/mysite.php:29`；`WordPressRestClient.php:271-274` |
| 重試間隔 | 100 毫秒（程式註明為暫定值） | `WordPressRestClient.php:29-30`、`266-269`（`Sleep::usleep`） |
| 會重試的情況 | 連線階段失敗（拒絕連線、無法解析主機、連線逾時、cURL 錯誤 6／7）；HTTP 5xx | `WordPressRestClient.php:107-113`（連線失敗）、`120-124`（5xx）、`232-238`（連線階段判定） |
| 不重試的情況 | 已連上後的整體逾時（cURL 28）；404；401／403；其他 4xx；3xx；JSON 無效；回應過大；非 200 | `WordPressRestClient.php:22-23`（註解）、`126-135`、`177-219`、`239-242` |
| 程式自算的最壞值 | `worstCaseSeconds()`＝2×5＋1×0.1＝10.1 秒 | `WordPressRestClient.php:81-87`；測試 `app/tests/Unit/Content/WordPressRestClientTest.php:262-268`（斷言 10.1，且嘗試次數設 99 時仍為 10.1）；CI 證據 `docs/evidence/gha-41984011065-1-content/results.jsonl` 第 428 行 PASS |
| 環境變數可調範圍 | 連線 1～10 秒、總時限 1～30 秒 | `app/app/Support/Config/MysiteConfig.php:79-80`；`docs/設定目錄.md:24-25` |

5 秒是 HTTP 用戶端（Guzzle）的 `timeout` 選項，也就是整個請求的總時限，已含連線階段；2 秒的 `connect_timeout` 只是其中連線階段的上限。程式第 232 行註解也寫明「已連上後的整體逾時不重試」。

### 1.2 各失敗路徑的單次上限

| 第一次嘗試的結果 | 是否重試 | 單次呼叫上限 |
|---|---|---|
| 回 5xx（最晚在 5 秒時限內回來） | 是 | 5＋0.1＋5＝**10.1 秒（W）** |
| 連線逾時（2 秒） | 是 | 2＋0.1＋5＝7.1 秒 |
| 拒絕連線、無法解析主機（幾乎立即） | 是 | 約 0＋0.1＋5＝5.1 秒 |
| 整體逾時 | 否 | 5 秒 |
| 404、401／403、其他 4xx、3xx、JSON 無效、回應過大 | 否 | 5 秒以內 |

佐證：`real_socket_total_timeout_is_bounded_and_not_retried`（`WordPressRestClientTest.php:273-296`）以真實 TCP 連線、總時限設 1 秒，驗證只嘗試一次且沒有重試等待；CI 耗時 1.02 秒（`results.jsonl` 第 429 行）。重試行為另有 `server_errors_are_retried_once_then_fail_with_503`、`connection_failures_are_retried_once`、`total_timeouts_are_not_retried` 三項（同檔第 417、419、420 行，皆 PASS）。

**查核結論**：§4.8 的「單次最壞＝第一次 5 秒＋0.1 秒＋第二次 5 秒；只有連線失敗與 5xx 重試；逾時不重試、上限 5 秒」與現行程式一致。以下記 **W＝10.1 秒**。

若日後改了 `CONTENT_HTTP_TIMEOUT_SECONDS`（記為 T），W＝2T＋0.1，本文件所有數值須重算。

## 2. 快取與可見性租約對冷快取呼叫次數的影響

| 快取 | 期限 | 冷快取時的效果 | 出處 |
|---|---|---|---|
| 快取存放處 | — | `CACHE_STORE=database`：每次讀寫快取是一次 MySQL 查詢，計入 Laravel 自身處理時間 L，不算 WordPress 呼叫 | `infra/compose.base.yml:26` |
| 列表類快取（列表、搜尋、分類總表、選單、站台資訊） | 等於租約秒數：`visibility_ttl` 30 秒（硬上限 60） | 值內含內容世代號；抓取失敗不快取、沒有舊值後備。冷快取時每一項各打一次 WordPress | `app/app/Domain/Content/Cache/ContentCache.php:11-19`、`32-42`、`72-85`；`app/config/mysite.php:31-32` |
| slug→id 對照 | 30 秒 | 未命中就要以 slug 查詢 | `ContentCache.php:87-101` |
| 可見性租約 | 30 秒（硬上限 60） | 沒有未過期的租約，就同步呼叫 visibility 端點 | `ContentCache.php:109-127`；`app/app/Domain/Content/ContentRepository.php:127-134` |
| 正文快取 | 300 秒 | 冷快取時沿用 slug 查詢取得的正文，不另外呼叫 | `app/config/mysite.php:33`；`ContentCache.php:44-47`、`130-145`；`ContentRepository.php:101-112` |

**單篇的冷快取流程**（`ContentRepository.php:86-120`）

1. slug 對照未命中 → `fetchDetail` 呼叫 `GET /{posts|videos|podcasts|pages}?slug=…&per_page=1`（第 160 行）。WordPress 外掛在帶 slug 查詢時回傳含 `body_html` 的完整內容（`wp/plugins/site-content/includes/rest-public.php:375`、`379`），所以程式在第 172-174 行直接返回，不會走第 176 行的 `GET /{endpoint}/{id}`。
2. 可見性租約未命中 → 呼叫 `GET /content/{type}/{id}/visibility`（第 99 行 → 第 134 行）。
3. 正文快取未命中 → 沿用第 1 步取得的資料（第 103 行），不再呼叫。

→ 單篇冷快取＝**依序 2 次**。

**「上游不可用」旗標**：WordPress 呼叫遇到連線失敗、逾時、5xx、JSON 無效、回應過大、3xx、非預期狀態時，會在當次請求標記 `mysite.content_upstream_failed`（`WordPressRestClient.php:258-264`；分類見 `app/app/Domain/Content/Http/UpstreamException.php:29-32`）。這個旗標只讓同一請求之後的「版型後備」（選單、站台資訊）直接改用內建值、不再呼叫 WordPress（`app/app/Domain/Content/ContentQueryService.php:208-213`）；內容類呼叫失敗時本來就拋出例外、中止請求。因此**最壞情況不是失敗，而是「每一次呼叫都慢、但最後成功」**（例如第一次在接近 5 秒時回 5xx，第二次又在接近 5 秒時成功）。

**全部依序**：`app/app` 底下沒有 `Http::pool`、非同步請求或 `Concurrency` 的用法（以全文搜尋確認），PHP 同步執行，每一次呼叫都等前一次結束。

補充說明：

### 3.1 單篇的邊界路徑（不是冷快取，但次數可能更多）

1. **防禦路徑**：若 WordPress 在 slug 查詢時沒有附 `body_html`（現行外掛會附，程式保留這條防禦路徑），會多打 `GET /{endpoint}/{id}`（`ContentRepository.php:176`），冷快取變成 3 次。
2. **slug 改指向另一筆**：slug 對照仍在 30 秒內有效、指向舊 id A（例如內容事件遺失或延遲，世代號未遞增），而 A 的租約已過期 → `visibility(A)`；A 的正文版本落後或 slug 不符 → 以 slug 重新查詢；查到新 id B ≠ A → `visibility(B)`（`ContentRepository.php:99-109`）。現行外掛下為 3 次；若同時走上第 1 點的防禦路徑，最多 4 次。

→ 冷快取的 2 次不是單篇程式路徑的上限；**程式路徑上限是 4 次**，只會出現在「slug 被改指、且內容事件沒有送達」的短暫窗口。

## 4. 最壞耗時試算

### 4.1 符號

| 符號 | 意義 | 值 |
|---|---|---|
| W | WordPress 單次呼叫最壞耗時 | 10.1 秒（§1） |
| N_x | 端點 x 對 WordPress 依序呼叫的次數 | §3 |
| L_x、L_site | Laravel 自身處理時間（框架啟動、資料庫快取讀寫、DTO 驗證、HTML 淨化、JSON 輸出） | **未量測**。儲存庫內沒有可引用的單一請求實測值；CI 證據裡的整合測試耗時（例如 `public_pages_render_real_content_over_http` 0.67 秒，`results.jsonl` 第 684 行）包含多個請求與測試準備，不能當作單一請求的 L |
| J | 前端 JSON 解析與驗證時間 | 未量測 |
| R | 前端畫面產生與送出回應的時間 | 未量測 |

算式（§4.8）：

- 端點最壞耗時 E_x＝N_x × W＋L_x
- site 部分 E_site＝3 × W＋L_site＝30.3＋L_site
- 前端並行取 site 與內容端點的資料等待 D_x＝max(E_site, E_x)

### 4.2 各頁型

| 代號 | 頁型 | N | 端點最壞 E_x（秒） | 與 site 並行的資料等待 D_x（秒） | 哪一方較大 |
|---|---|---|---|---|---|
| A | 站台資訊與選單 | 3 | 30.3＋L_site | — | — |
| B | 首頁（現行動作，含 `/site`） | 4 | 40.4＋L_home | max(30.3＋L_site, 40.4＋L_home) | 內容端點；除非 L_site 比 L_home 多 10.1 秒以上 |
| B′ | 首頁（不含 `/site`） | 3 | 30.3＋L_home | 30.3＋max(L_site, L_home) | 看 L 何者較大 |
| C | 列表 | 1 | 10.1＋L_list | max(30.3＋L_site, 10.1＋L_list) | site；除非 L_list 比 L_site 多 20.2 秒以上 |
| D、E | 單篇、一般頁面（冷快取） | 2 | 20.2＋L_d | max(30.3＋L_site, 20.2＋L_d) | site；除非 L_d 比 L_site 多 10.1 秒以上 |
| D、E | 單篇、一般頁面（防禦路徑，§3.1 第 1 點） | 3 | 30.3＋L_d | 30.3＋max(L_site, L_d) | 看 L 何者較大 |
| D、E | 單篇、一般頁面（程式路徑上限，§3.1 第 2 點） | 4 | 40.4＋L_d | max(30.3＋L_site, 40.4＋L_d) | 內容端點；除非 L_site 比 L_d 多 10.1 秒以上 |
| F、H | 分類總覽、標籤總覽 | 4 | 40.4＋L_t | max(30.3＋L_site, 40.4＋L_t) | 內容端點；除非 L_site 比 L_t 多 10.1 秒以上 |
| G、I | 分類、標籤指定型別 | 2 | 20.2＋L_t | max(30.3＋L_site, 20.2＋L_t) | site；除非 L_t 比 L_site 多 10.1 秒以上 |
| J | 搜尋（有查詢詞） | 1 | 10.1＋L_q | max(30.3＋L_site, 10.1＋L_q) | site；除非 L_q 比 L_site 多 20.2 秒以上 |
| K | 搜尋（不查詢） | 0 | L_q | max(30.3＋L_site, L_q) | site；除非 L_q 比 L_site 多 30.3 秒以上 |

## 5. 與 60 秒上限的距離與沿途時限

| 環節 | 時限 | 出處 |
|---|---|---|
| 瀏覽器 → gateway → 前端 | gateway `proxy_read_timeout 60s` | `infra/nginx/common/gateway-proxy.conf:15` |
| 前端 → app-web（直連 `/api/v1/`，定案執行書 §3.3 查核 13、v1 §4.6） → PHP-FPM | app-web `fastcgi_read_timeout 60s` | `infra/nginx/common/fastcgi-common.conf:6`（由 `infra/nginx/app-web.conf:49` 引入） |
| PHP-FPM 單一請求 | `request_terminate_timeout = 60s`（實際經過時間） | `infra/php/www.conf:19` |
| PHP `max_execution_time` | 30 秒 | `infra/php/runtime.ini:4` |

`max_execution_time` 在 Linux 上只計腳本自身的執行時間，不含等待網路回應的時間（PHP 手冊 `set_time_limit` 說明）。本次以本機 PHP 8.3.6 CLI 實測：`max_execution_time=1` 時，curl 等待 3 秒後才以逾時結束，腳本沒有被中止。這不是專案使用的 PHP 8.5.12 FPM 容器，結果僅供參考；照此推論，它不會截斷等待 WordPress 的時間。

**距離**：最壞內容端點 40.4 秒＋L_x，離 60 秒還有 **19.6 秒**，須容納 L_x、J、R 與各段網路開銷；只看 site 部分（30.3 秒＋L_site）則還有 29.7 秒。

## 6. 結論（供 D13c 裁定）

- **最壞頁型**：分類總覽與標籤總覽（未帶 `type`），對 WordPress 依序 4 次。首頁若內容端點保留現行動作內的 `/site` 呼叫，同為 4 次；單篇只在 §3.1 第 2 點的邊界窗口才會到 4 次。
- **最壞資料等待**：D_max＝max(3W＋L_site, 4W＋L_x)＝**max(30.3＋L_site, 40.4＋L_x) 秒**；當 L_x＋10.1 ≥ L_site 時＝40.4＋L_x。
- **前端逾時下限**：前端逾時＞D_max＋J＝**max(30.3＋L_site, 40.4＋L_x)＋J**。
- **整頁上限條件**：整頁處理須小於 gateway `proxy_read_timeout 60s`，即 D_max＋J＋R＜60；以最壞頁型代入為 40.4＋L_x＋J＋R＜60，也就是 **L_x＋J＋R＜19.6 秒**。
- 數值由委託人裁定（D13）；本文件不建議前端逾時值。

3. **L、J、R 都沒有實測值**。
