## 1. D13a：next 模式的搜尋限流

**現況**：Laravel `content-search` 每 IP 每分鐘 30 次（`app/app/Providers/ContentServiceProvider.php` 的 `SEARCH_PER_MINUTE = 30`、`RateLimiter::for('content-search', …)`）。next 模式下 Laravel 看到的來源是前端容器，所以每 IP 限流必須移到 gateway；公開 API 的搜尋已不在 Laravel 限流（`app/routes/api.php` 註解、`docs/公開API契約.md` 第 2 節）。

**提議**：

| 設定 | 提議值 | 算式／理由 |
|---|---|---|
| `limit_req_zone` 鍵 | `$binary_remote_addr` | gateway 直接面對訪客，`$remote_addr` 就是訪客位址（gateway 沒有 real_ip，定案 §3.3 查核 13） |
| 區域大小 | `10m` | 沿用 gateway 現有登入限流區 `mysite_login:10m`（`infra/nginx/gateway/http/gateway.conf.template`）；nginx 官方文件（https://nginx.org/en/docs/http/ngx_http_limit_req_module.html ，2026-11-06 查）：1 MB 約可存 1.6 萬個 64 位元組或 8 千個 128 位元組的狀態，10 MB 約 8 萬～16 萬個位址；用盡時淘汰最久未用的狀態 |
| `rate` | `30r/m` | ＝`SEARCH_PER_MINUTE` 次／分鐘，長期平均與 Laravel 相同 |
| `burst` | `29`，搭配 `nodelay` | ＝`SEARCH_PER_MINUTE − 1`：第一分鐘可立即用完 30 次（1 次本身＋29 次突發），與 Laravel 固定時間窗「每分鐘 30 次」的第一分鐘容量相同；之後每 2 秒補 1 次 |
| 適用位置 | `/search` 與 `/_next/data/*/search.json` 共用同一區（定案 §6 F6 第 1 項） | 兩條路算同一份額度 |
| 超限回應 | 429，`error_page 429` 指向正體中文頁（比照 `infra/nginx/maintenance/index.html` 的做法） | v1 D13a |

**兩種演算法的差異（照實寫，F6 以測試記錄）**：nginx `limit_req` 是漏桶，Laravel 是固定時間窗。以「任一 60 秒內最多幾次」比較：Laravel 在時間窗交界可連續 30＋30＝60 次；nginx 在桶滿時先 30 次、再以每 2 秒 1 次補充，60 秒內最多 30＋30＝60 次。長期平均兩者都是每分鐘 30 次；差別在 nginx 的補充是均勻的，Laravel 是每分鐘整批重置。

**要委託人裁定**：是否採 `rate=30r/m`、`burst=29 nodelay`、區域 `10m`。

## 2. D13f：兩張新網路與相關名稱

**現行編排慣例**（`infra/compose.base.yml`、`scripts/cloud/bootstrap.sh`、`scripts/lib/deploy.sh`）：

| 網路 | 子網 | internal |
|---|---|---|
| edge | `172.<環境>.10.0/24`（gateway 固定 `.10`，動態位址只從 `.128/25` 分配） | 否 |
| backend | `172.<環境>.20.0/24` | 是 |
| db | `172.<環境>.30.0/24` | 是 |

`<環境>` 是第二個八位元：development 30、testing 31（`bootstrap.sh`）；主機部署 production 30、其他 29（`deploy.sh`）。四種環境的位址段因此互不衝突。

**提議**：第三個八位元沿用「10 的倍數、依序遞增」：

| 用途（v1 §4.6） | 網路名稱 | 子網 | internal | 成員 |
|---|---|---|---|---|
| gateway↔前端 | `frontend` | `172.<環境>.40.0/24` | 是 | gateway、前端容器 |
| 前端↔app-web API | `frontend-api` | `172.<環境>.50.0/24` | 是 | 前端容器、app-web |

| 其他名稱 | 提議 | 理由 |
|---|---|---|
| 前端服務名稱（compose） | `web-next` | 與 `app-web`、`wp-web` 的「用途-web」命名一致，`next` 表示渲染模式值 |
| app-web 在 `frontend-api` 上的專用別名 | `public-api` | v1 §4.6：前端只用這個別名連線；名稱表明只能用公開 API |
| 環境變數 | `FRONTEND_SUBNET`、`FRONTEND_API_SUBNET` | 比照 `EDGE_SUBNET`、`BACKEND_SUBNET`、`DB_SUBNET`；部署端的格式檢查（`deploy.sh` 只接受 172.16～31 的 /24）一併沿用 |

各環境實際值：development `172.30.40.0/24`、`172.30.50.0/24`；testing `172.31.40.0/24`、`172.31.50.0/24`；production `172.30.40.0/24`、`172.30.50.0/24`；其他主機部署 `172.29.40.0/24`、`172.29.50.0/24`。同一台主機上同時只會有一個主機部署環境，development 與 testing 只在雲端 VM 與 CI，不與主機部署並存。

**要委託人裁定**：兩張網路的名稱與子網、前端服務名稱 `web-next`、app-web 別名 `public-api`、兩個環境變數名稱。裁定後才在 F6 寫進 compose 與 gateway（`geo` 斷線用的網段也依此值，定案 §4.5）。
